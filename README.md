# ParallelRoom

同一个抖音账号**并行进入多个直播间、都不退出**的桌面工具（自用/内部，Electron）。

> 功能现状与待办清单见文末「[还没做的（待办 / 已知缺口）](#还没做的待办--已知缺口)」。

## 录制

每个房间磁贴标题栏有 `⏺` 按钮，点一下开始、再点停止。录制有**两种模式**，自动选择：

**整窗录制**：工具栏「录窗口」按当前布局把**各瓦片的视频区拼成一张干净的画面**——不含顶部工具栏、不含瓦片标题栏、不含瓦片之间的间隙。

做法是录整窗捕获流，再按每个 `.stage` 的矩形把内容画进一块新 canvas：列/行位置取自各瓦片实际的 x/y，单元尺寸取最大瓦片尺寸，所以输出是无缝网格。实测 4 个瓦片（各 838×410 CSS）拼成 **2514×1230**（2 列 × 2 行 × DPI 1.5）、29fps、带系统声音。

因为要重编码，**同时只能录 1 路**，且与单房间的屏幕兜底录制互斥（直录流不受影响）。想让每个房间各自成文件、拿到 1080p 原画，用瓦片上的 `⏺` 直录流。

**并发**：可以多个房间同时录。直录流每路只是一个 ffmpeg 进程（`-c copy` 不转码），**最多同时 8 路**；屏幕捕获因为要解码+重编码，**同时只允许 1 路**。实测 3 路同时录 25 秒，产出 3 个 1080p60 文件：```
dota pk4丶_...mp4        16.59 MB
dota大熊小清新_...mp4     28.47 MB   1920x1080 hevc 60fps + aac 2ch  28.5s
dota老花一打九_...mp4     19.40 MB
```

工具栏「停止录制」可一次停掉所有正在进行的录制；每个瓦片上的 ⏹ 只停自己那一路。

**输出位置**：默认存到 **项目目录下的 `output/`**（`D:\code\ParallelRoom\output`），「⚙ 录制选项」里可以改到任意位置，选择结果写进 state.json。

| | **stream 直录流**（默认） | **screen 屏幕捕获**（兜底） |
| --- | --- | --- |
| 触发 | 能拿到该房间的 FLV 地址 | 拿不到流地址时自动回退 |
| 画质 | **1920×1080 HEVC 30–60fps**，= 平台原画 | 1186×1170 ~ 2386×1170 H.264 29fps（受窗口像素限制） |
| 音频 | **AAC 立体声，属于该房间自己的音轨** | 系统 loopback 混音，单声道 |
| CPU | 极低（`-c copy` 只转封装，不重编码） | 中高（逐帧绘制 + 重编码） |
| 是否占窗口 | 不占 | 会自动把该房间放大 |

实测两条路的结果：

```
stream:  1920x1080 hevc 30fps + aac 2ch   15.5s  9.21MB  4.99 Mbps   转封装秒级完成
screen:  2386x1170 h264 29fps + aac 1ch   12.2s  9.67MB  6.65 Mbps   ffmpeg 重编码
```

### 录制是怎么落盘的（每次一个目录 + 分段 + 自动合并）

**每次录制建一个目录**，目录名 = 直播间名 + 录制开始时间戳，分段和成片都放在里面：

```
D:\code\ParallelRoom\output\DOTA情怀_20261030-165549\
    part000.mkv   part001.mkv   part002.mkv …      ← 每 5 分钟一个（可调：2/5/10/30 分钟或不切段）
              ↓  停止时 / 断流放弃时自动合并
    DOTA情怀_20261030-165549.mp4                    ← 你最终看到的文件（分段随后删掉，目录保留）
```

分段目录放在**录制目录**里而不是 `%TEMP%`：录了什么、到第几段了，进目录就能看见，程序崩溃也不会被"清理临时目录"连带清掉。

实测（分段调成 6 秒、录 15 秒）：

```
录制中   目录内容 = ["part000.mkv","part001.mkv","part002.mkv"]
停止后   目录内容 = ["目录测试_20261030-172223.mp4"]   ← 分段已合并删除
剪辑页签 listRecordings 读到 → group=目录测试_20261030-172223  rel=目录测试_…/目录测试_….mp4
```

为什么要分段，而不是像以前那样一个几 GB 的 mkv 录到底：

| | 以前（单文件） | 现在（分段） |
| --- | --- | --- |
| 断电 / 强杀 | 只有尾部损坏也要全量重封装，且重启后才知道文件在哪 | 已封好的段都在，最多丢当前这一小段 |
| 断流自动续录 | 每续录一次就多一个独立 mp4，得自己再拼 | 续录接着往**同一个会话目录**里编号，最后自动合成一个 mp4 |
| 落盘时机 | 停止时才封装 | 每满一段就有一个完整、可直接播的 mkv |

分段用 ffmpeg 的 `-f segment -segment_time 300 -segment_format matroska -reset_timestamps 1`（`-c copy`，不重编码，所以切段几乎不花 CPU）。停止时把各段用 concat 解复用器 `-c copy` 串成一个 mp4 并删掉分段。

实测（`segmentMs` 调成 8 秒，录 26 秒）：

```
+6s   会话目录: ["part000.mkv"]
+26s  会话目录: ["part000.mkv","part001.mkv","part002.mkv","part003.mkv"]
停止  stream record done { parts: 4 }  → 分段测试_161549.mp4  28.161s / hevc 1920x1080
      会话目录已清理
```

残留恢复现在覆盖三种中转文件：会话目录里的 `part*.mkv`（多段拼接）、老格式的散装 `.mkv`（直接封装）、屏幕/整窗录制的 `.webm`（转码）。实测救回过一段被打断的屏幕录制：

```
[rec] recovering orphan recording {"kind":"webm","name":"Dota孤城大神_20261030-164937.webm","bytes":121037350}
[rec] recovered orphan recording  {"mp4":"...\\output\\Dota孤城大神_20261030-164937.mp4"}
ffprobe: h264 2506x1172 + aac, duration=95.87s
```

同一房间"开录→停止→再开录"也验过（`actives` 归零、看门狗自动关），不会再出现"这个房间已经在录制了"的假占用。

### 水印（只在剪辑页签加）

**录制阶段不烧水印**——录制永远走 `-c copy`（零转码）。水印全部在「剪辑」页签做：录制时重编码白烧 CPU，而且水印想改一次就得重录一遍。

| 入口 | 能力 |
| --- | --- |
| 「剪辑」页签 → 水印设置 | **全部能力**：文字 / 图片 Logo / 文字+图片，九宫格位置、字号、颜色、透明度、边距、阴影、图片缩放、**只在指定时间段显示** |
| 「剪辑」页签 → 勾「合并时一起加水印」 | 合并 + 水印**一步做完**：解码、拼接、画水印、重新编码只跑一遍（比"先合并再加水印"少一次转码、少一次质量损失） |
| 「剪辑」页签 → 「单独加水印」 | 不合并，只给选中的文件加水印 |

可定制项一览：

| 项 | 范围 | 说明 |
| --- | --- | --- |
| 类型 | 文字 / 图片 / 文字+图片 | 图片 PNG 支持透明通道 |
| 文字 | 任意 UTF-8 | 字体自动找 `msyh.ttc → simhei.ttf → simsun.ttc → arial.ttf`（`PR_WM_FONT` 可覆盖） |
| 位置 | 九宫格（左上…右下） | 文字和图片同角时，图片自动让开一个字高 |
| 字号 / 边距 | 8–200 px / 0–200 px | |
| 颜色 / 透明度 | `#RRGGBB` / 0.05–1 | |
| 阴影 | 开/关 | 亮背景上也能看清 |
| 图片缩放 | 画面宽度的 3%–60% | 用 ffprobe 量出实际画面宽度再按像素缩放 |
| 时间段 | `fromSec` / `toSec` | 只有这一段时间里出现（做片头/片尾水印用） |

生成的滤镜串示例（文字 + 图片 + 限时 2–8 秒）：

```
[0:v]drawtext=fontfile='C\:/Windows/Fonts/msyh.ttc':text='水印测试':fontcolor=0xFFFFFF@0.85:fontsize=28:x=20:y=h-th-20:shadowcolor=black@0.85:shadowx=2:shadowy=2[t];
[1:v]scale=230:-2:flags=lanczos,format=rgba[logo];
[t][logo]overlay=20:H-h-20-36:format=auto:enable='gte(t\,2)*lte(t\,8)'[vout]
```

> ⚠️ 踩过的坑：图片缩放一开始用 `scale2ref`，ffmpeg 8.1 里它已废弃，**叠上去的图完全看不见**（不报错，静默失效）。实测对照——同一张红色 logo：
>
> | 写法 | 左下角区域平均色 |
> | --- | --- |
> | 原片（无 logo） | `RGB(45,90,58)` |
> | `[0:v][1:v]overlay`（不缩放） | `RGB(200,23,19)` ✅ 可见 |
> | `scale2ref=w=main_w*0.12:h=ow/mdar` | `RGB(45,89,57)` ❌ 和原片一样 |
> | `scale=230:-2`（现在用的） | `RGB(242,5,5)` ✅ 可见 |
>
> 现在改成先用 ffprobe 量出画面宽度，再按像素 `scale`，并用像素采样验证了可见性和时间段：
>
> ```
> 图文水印 t=1 （窗口外）: RGB(42,91,59)   ← 原色
> 图文水印 t=5 （窗口内）: RGB(241,3,2)    ← 红色 logo 在
> 图文水印 t=10（窗口后）: RGB(44,44,44)   ← 回到原色
> ```
>
> 文字水印也验过：右下角区域 `RGB(87,84,68) → RGB(92,86,60)`（往 #FFCC00 的黄偏），字体渲染单独测过三个字符 MD5 各不相同，不是豆腐块。

### 「剪辑」页签（选目录 / 合并 / 加水印）

顶部页签第三个是**剪辑**，左边文件列表、右边水印设置：

- **选目录**：默认是录制目录，可以切到任意目录；改过的目录记在 `state.json` 的 `editDir`
- **文件列表**：按录制目录分组显示（`<主播>_<时间戳>/xxx.mp4`），录制中的会显示成 `（录制中）N 个分段` 并且不可选
- **合并选中**：`-c copy` 纯封装，几秒钟；要求编码参数一致
- **加水印**：对选中的文件重编码加水印，输出到原文件同目录（默认名 `原文件名_水印.mp4`）

实测：`wm-text.mp4`(17.9s) + `…_水印.mp4`(17.9s) → `合并测试.mp4` **35.7s**、14.51MB = 7.34 + 7.17，正好是两段之和。

**方案说明（为什么水印一定要重编码）**：直播流录制走的是 `-c copy`（零转码，1 路 1080p 只占很低的 CPU）。任何"画上去"的东西——文字、图片、时间戳——都必须解码→合成→重新编码，所以：

- 录制时打水印：CPU 显著上升，1080p 单路 `veryfast` 大致能跑，多路会吃满 CPU
- 已经有录像再加水印：不受实时限制，慢一点无所谓
- 想要"零转码 + 有水印"，只能做**软水印**（写进 mp4/mkv 的 metadata 标签），播放器不一定会显示——这个我没做，也不建议

### 快捷键

| 快捷键 | 作用 |
| --- | --- |
| `Ctrl+Shift+R` | 录制/停止**鼠标所在的那个瓦片**；鼠标不在任何瓦片上时退化为"当前放大的那个"，都没有则提示 |
| `Ctrl+Shift+S` | 停止全部录制 |
| `Ctrl+Shift+W` | **整窗录制 开/关**（不用管鼠标在哪；和「录窗口」按钮等效） |
| `Ctrl+Shift+H` | 显示/隐藏顶部工具栏（任何状态下都可用） |
| `F11` | 全屏观看（`Esc` 退出） |
| `F1` / `?` | 打开**快捷键帮助面板**（工具栏「? 快捷键」按钮同效） |
| `1`~`9` | 聚焦布局下把第 N 号瓦片换到中间（编号就是瓦片左上角那个数字） |
| 双击瓦片顶栏 | 单间放大 / 还原 |
| 右键瓦片顶栏 | 这个房间单独设画质 |
| `Esc` | 退出单间放大 / 关掉帮助面板 / 关掉小菜单 |

前四条在主进程的 `before-input-event` 里拦截，**主窗口和每个 webview guest 都挂**，所以焦点在抖音画面里也能用。鼠标定位靠 `screen.getCursorScreenPoint()` 减窗口内容区坐标，再到渲染层换算成具体瓦片。

`F1` / `?` 也一样走主进程 → 发 `ui:open-help` 给渲染层，否则焦点在 guest 里时按了没反应。`1`~`9` 和 `Esc` 在渲染层处理（焦点在 guest 里时按数字会被抖音页面吃掉，这是已知限制——点一下画面外面的顶栏再用）。

帮助面板里列了全部快捷键和常用操作（3 组、13 行），内容就是上面这张表。

实测：按钮打开 ✓ / `Esc` 关闭 ✓ / `?` 打开 ✓ / `F1` 打开 ✓；聚焦布局下按 `2` → 主画面变成第 2 块，按 `3` → 第 3 块。

实测鼠标定位：鼠标停在第 2 个瓦片按 `Ctrl+Shift+R`，启动的是第 2 个房间（`uid: r2`），不是默认第一个。

### 时长上限与磁盘保护

| 机制 | 默认 | 实测 |
| --- | --- | --- |
| 单次录制时长上限 | 60 分钟 | 设成 12 秒测试，12 秒整触发自动停止，文件正常落盘（26.74MB） |
| 开录前磁盘检查 | 剩余 < 2 GB 拒绝开录 | 把安全线调到 10 TB 后返回 `磁盘剩余 54.2 GB，低于安全线 10240.0 GB，请清理空间或换录制目录` |
| 录制中磁盘复查 | 每 30 秒一次 | 跌破安全线即停止全部录制并提示 |

每条录制有独立的到点计时器（不依赖 30 秒一次的巡检，所以到点是精确的）。环境变量可覆盖：`PR_REC_MAX_SEC`（秒）、`PR_REC_MIN_FREE_MB`（MB）。

### stream 模式怎么拿到流地址

直播页会去拉 HTTP-FLV（`pull-flv-*.douyincdn.com/thirdgame/stream-xxx.flv?expire=&sign=`）。主进程在该 session 上挂 `webRequest.onBeforeRequest`，按 `webContentsId` 记下每个页面**最近一次**请求到的流地址；点录制时按瓦片对应的 guest id 取出来，直接喂给 ffmpeg：

```
ffmpeg -user_agent <UA> -headers "Referer: <room url>" -i <flv> -c copy -f matroska tmp.mkv
# 停止后：ffmpeg -i tmp.mkv -c copy -tag:v hvc1 -movflags +faststart out.mp4
```

中间存 `.mkv` 而不是直接存 mp4，是因为 mp4 的 moov 需要写文件尾，进程被 kill 会留下损坏文件；mkv 抗中断，停止后再无损转封装成 mp4。

地址带签名 `expire=`，**实测有效期约 7 天**（`1793951397 - 抓取时刻 ≈ 608326 秒`）。代码里超过 **6 小时**才视为过期，回退屏幕录制。这本质上是"抓流"而不是"录屏"，自用没问题，性质上更接近下载器。

> ⚠️ 踩过的坑：这里原来只认 **30 分钟**。看完一小时再点瓦片上的 `⏺` → 地址被判过期 → 回退**屏幕录制** → 而屏幕录制必须把这块画面放大 → 用户看到的就是「**点录制按钮变成窗口最大化**」。
>
> 现在三件事一起改了：
> - 有效期 30 分钟 → **6 小时**（实测 45 分钟 / 200 分钟的地址都仍可直录，400 分钟才回退）
> - 真的需要回退屏幕录制时，状态栏会明说：`还没抓到这个房间的直播流地址 → 改用屏幕录制（这块画面会自动放大；想要原画就重载房间后再录）`
> - 地址彻底失效时不再白重试 5 次：一次尝试**一个字节都没收到**就立刻放弃并提示（实测 1.1 秒收手，而不是退避 3+6+12+24+30 秒）

### ⚠️ 断流 / 卡死 / 退出 三种丢录制的情况（已修）

用户实测反馈「一直在看，画面也在播，卡了一下录制就没了」。查下来是三个独立的坑叠在一起：

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 录到 **15~16 分钟**就没了（两段分别 15:26 / 16:09） | ffmpeg 那条长连接被对端关掉，`close` 后只做一次封装就结束了，没有重连 | **自动续录**：断流后按 3→6→12→24→30 秒退避，用最新的流地址接着录新的一段，最多 5 次；放弃时明确提示"已保存 N 段" |
| 画面不卡、**录制实际停了**，界面还显示在录 | 网络卡住时 ffmpeg 会一直等，既不退出也不写数据 | **卡死检测**：每 30 秒看一次 ffmpeg 自己打的 `time=HH:MM:SS` 进度，60 秒不前进就杀掉 ffmpeg → 封装这一段 → 自动续录 |
| 关掉程序后录制**整段不见** | 退出时直接 `SIGKILL` ffmpeg，数据只剩临时目录里的 mkv，永远没人封装 | 退出时给 ffmpeg 发 `q` 并等最多 2.5 秒收尾；来不及封装的**下次启动自动补封装**（`recoverOrphans()`） |

还有一个独立的硬伤：封装命令写死了 `-tag:v hvc1`，那是 HEVC 的封装标签。抖音有的房间是 **H.264**，带着它必失败：

```
Tag hvc1 incompatible with output codec id '27' (avc1)
Could not write header (incorrect codec parameters ?)
```

`DOTA情怀`(485185918272) 就是 H.264，所以它的录制**每次都封装不出来**。现在封装失败会去掉标签重试一次。

现场恢复的实证（都是真实丢过的数据）：

```
[rec] recovering orphan recording {"mkv":"...\\DOTA情怀_20261030-151638.mkv","bytes":5756299573}
[rec] remux retry without hvc1 tag {...}
[rec] recovered orphan recording {"mp4":"D:\\code\\ParallelRoom\\output\\DOTA情怀_20261030-151638.mp4","bytes":5756299573}
recoverOrphans {"ok":true,"recovered":1,"failed":[]}
```

`ffprobe` 复核：`h264 / 1920x1080 / aac / duration=1845.66s`（30 分 46 秒 / 5.36 GB），另有三段昨晚的残留 mkv 也一并补回了 `output/`。

自动续录的实测（连续 6 次杀掉 ffmpeg 模拟断流）：

```
kill #1 → stream record done (6.6MB)  → will resume in 3000ms  (第 1 次)
kill #2 → stream record done (5.1MB)  → will resume in 6000ms  (第 2 次)
kill #3 → ... 12000ms → kill #4 → 24000ms → kill #5 → 30000ms → kill #6
kill #6 → stream retries exhausted → 「流断了，自动续录 5 次仍失败，录制已停止（已保存 6 段到录制目录）」
final: actives=0 pending=0   —— 不会无限重试
```

每次断掉的那一段都会被封装成独立 mp4 落进 `output/`，临时目录不留孤儿。录制事件的日志写在 `%APPDATA%\ParallelRoom\rec.log`（常开，不依赖 `PR_LOG`，2MB 轮转），下次再出问题可以直接回溯。

### 屏幕捕获模式的两个坑（已修）

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 13 秒只录到 **14 帧**（≈1fps） | recorder 是隐藏窗口，`requestAnimationFrame` 被节流 | 改 `setTimeout` 定时驱动 |
| ffmpeg 报 `width not divisible by 2 (1187x1171)` | h264 要求偶数尺寸 | canvas 裁成偶数 + `pad` 兜底 |

### 声音

**stream 模式天然每路独立**（录的是该直播间自己的流，音轨就属于它），不需要虚拟声卡。

**screen 模式**只能取 Windows 系统 loopback，是所有房间混音后的一路，且为单声道，录制阶段无法拆分。

### 只开一个房间却听到别的声音？按这个顺序查

1. **调试页 → 区块 1**：某个瓦片「同时出声的音源数」> 1 → 是这个页面自己多音源；若只有你开的那个房间是 1，声音多半不是这个窗口发的。
2. **区块 2**：有没有你意料之外的 `webview` 还活着（旧房间的页面没释放）。
3. **区块 4 的进程数**：同一个 ParallelRoom 只允许跑一个实例（`requestSingleInstanceLock`，第二次启动只会把已有窗口切到前台，不会再开一个"在后台放声音"的窗口）；但用**不同数据目录**启动的副本、以及本机其它浏览器/客户端放的直播，声音会进同一个音箱 —— 这时用 Windows **设置 → 系统 → 声音 → 音量合成器** 看是哪个进程在响最直接。
4. 还是查不出来，点「保存快照」把那个 json 发我。

### 真凶之一：**监控探测窗在出声**（已修）

"只开了 Pis、却听到别的声音"最终查到了真凶：**监控页探测用的隐藏窗口在放声音**。它是 `BrowserWindow({ show: false })`，看着"没有窗口"，但 Chromium 里"隐藏"不等于"静音"。

实测（2026-10-31，沙箱 6 个房间连点两轮"全部检测"，同时监听探测窗口 `media-started-playing` / `isCurrentlyAudible()`）：

```
14:27:49.360  media-started  id=2  https://live.douyin.com/612630333230   ← 隐藏的探测窗开始播
14:27:49.850  audible=true   id=2  https://live.douyin.com/612630333230   ← 真的发声了
14:28:00.990  media-paused   id=2
14:28:01.195  audible=false  id=2  （这次探测结束，换下一个房间）
```

也就是说**每探一个在播房间，隐藏窗口可能响 10 秒左右**。你有 34 个监控房间、60 秒一轮，于是"看 Pis 的时候总能听到别的主播"，完全对得上。

为什么原来的媒体拦截没挡住：拦截只能按"扩展名 / `resourceType=media`"匹配（`MEDIA_RE`），而抖音有的房间走**无扩展名的 `pull-hls` 分片**，匹配不到；又不能为了拦干净就把规则加宽 —— 判活要用"6 秒内媒体流量 4.3MB"这个信号，拦宽了流量就没了，探测会把在播全部误判成未开播。

修法：**直接给这些隐藏窗口整个静音**（不碰拦截规则，流量照常计量、判活不受影响）：

| 窗口 | 位置 | 处理 |
| --- | --- | --- |
| 监控探测窗（`ProbeManager`） | `probe.js` `ensureWindow()` | `webContents.setAudioMuted(true)` |
| 关注列表探测窗（`FollowProbe`） | `probe.js` | 同上 |
| 屏幕/整窗录制窗（里面那个 `<video>` 本来就是 muted 的） | `recorder.js` | 同上，再兜一层 |

实测（同样 6 个房间、同样两轮检测）：

```
探测窗 muted=true（创建即静音，跨 40+ 次导航一直是 true，没有回弹）
中间仍可能看到 audible=true —— 注意 Electron 的 isCurrentlyAudible() 只表示"页面在产生音频"，
被静音时也可能是 true；判断有没有声音要看 muted。
```

顺带在调试页把这种窗口标出来了：第 2 区块里 `window` 类型会显示成 **`window（隐藏·后台窗）`**，一眼能认出探测/录制窗，`在出声/静音` 两列直接看状态。

## 关掉房间后还有声音？（声音卫兵）

现象：把观看页的房间全关了（✕ 或「清空」），却还听到某个直播间在响。

根本原因在于 **"元素被移除"和"guest 进程被销毁"不是同一件事**：`webview.remove()` 正常会顺带销毁 guest，但移除时机不对（页面卡住、渲染层抛异常、元素已经半脱落）时，元素没了、那个 `webContents` 还活着并继续解码音频——界面上一块瓦片都没有，声音却停不下来。

三层兜底（都在本次改动里）：

| 层 | 做法 | 效果 |
| --- | --- | --- |
| 1 | 关瓦片时**先 `setAudioMuted(true)`**，再 `stop()` / `remove()` | 立刻静音，不会听到"销毁前的尾巴" |
| 2 | 关闭时把 guest 的 `webContentsId` 记下来，调 `guest:kill` 让**主进程点名销毁**这个 webContents | 不依赖"移除 DOM 一定会销毁"这个假设 |
| 3 | 主进程每 4 秒对账一次：渲染层把"当前还活着的瓦片 guest id"报上来（`guest:sync`），**连续两轮都不在名单里**的 webview 页面直接 `close()` | 任何漏网的孤儿页面都会在 4–8 秒内被关掉，不会一直响 |

第 3 层故意要求"连续两轮"而不是一发现就杀：新开的瓦片从 `attach` 到被上报有几十毫秒的空档，太激进会把刚打开的房间静音/关掉（踩过这个坑的典型）。

动作会写在 **`%APPDATA%\ParallelRoom\guest-guard.log`**（超过 512KB 自动滚成 `.1`），只记"真的动手了"的事件，例如：

```
[2026-10-30T15:27:30.029Z] kill 3 (orphan sweep) via close
[2026-10-30T15:27:30.031Z] sweep done {"checked":1,"killed":1}
```

实测（4 个瓦片、故意把一块瓦片从 `tiles` 里摘掉并隐藏，制造"页面还活着但没人管"的孤儿）：

```
+0s    tiles.size=0，但 /json/list 里那个 live.douyin.com 页面还在播
+3.5s  第二轮对账：认定遗留
+5s    [guard] kill 3 (orphan sweep) via close
+5.2s  音频追踪只剩主窗口，audible=false，页面彻底消失
```

正常关闭四个瓦片的对照组：`media-paused` → `destroyed` → 主窗口 `audible=false`，一秒钟内安静；开着房间正常播放的这段时间里，卫兵**一次都没动手**（不会误杀正在看的房间）。

## 特别关注与探测策略（重要）

监控列表里的每张卡片可以点 **☆** 标为**特别关注**（本地标记，跟抖音的"关注"完全无关）。探测按这个优先级轮转：

- **每 3 轮里有 2 轮**探「特别关注」里最久没探过的那个 → 你真正关心的房间刷新最快
- 剩下 1 轮探一个非特别关注的老房间，避免其余房间状态彻底过期
- 默认间隔 120 秒探 1 个；32 个房间全部轮一遍约 1 小时，而 3 个特别关注的房间大约 3 分钟就能刷新一次
- 工具栏「只看特别关注」可以过滤视图
- 工具栏搜索框支持**按主播名 / 房间号 / 链接过滤**，多个关键词用空格隔开（AND 关系），`Esc` 清空；右侧会显示"匹配 N"

**为什么不能高频全量探测**：逐个加载直播间页面是最"重"的探测方式，之前一口气探 32 个（≈192 次/小时）直接把 IP 送进了验证码。现在的处理：

| 机制 | 说明 |
| --- | --- |
| 验证码识别 | 命中「验证码/滑块/安全验证」判为 `blocked`，**保留上次有效状态**，绝不覆盖成"未开播" |
| 指数退避 | 被拦后冷却 30 分钟 → 1 小时 → 2 小时 → 4 小时封顶，探成功一次立刻复位 |
| 冷却持久化 | 冷却时间写进 state.json，重启不会立刻再撞 |

## 瓦片数量与布局

- **最多 12 个瓦片**，超出会提示 `最多同时打开 12 个瓦片`，计数显示 `N / 12 个房间`
- 工具栏「布局」下拉可以**自定义行列数**：自动 / **中间大 · 右侧小窗** / 1×1 / 2×1 / 2×2 / 3×1 / 3×2 / 3×3 / 4×3
  - 选定的行列数 = **每屏显示多少个**，超出的瓦片按同一列数往下排，用滚动条查看
  - 选择会记住（localStorage）
  - 「自动」时的规则：普通窗口一屏放完（1→1列、2-4→2列、5-9→3列、10-12→4列）；全屏固定 3 列 × 2 行
- 觉得 12 个看不过来，就把布局调到 2×2（一屏 4 个）或 3×2（6 个），剩下的滚动查看

实测（全屏、8 个瓦片）：

| 布局 | 列数 | 瓦片高 | 每屏 | 可滚动 |
| --- | --- | --- | --- | --- |
| 自动 | 3 | 524px | 6 | 是 |
| 2×2 | 2 | 524px | 4 | 是 |
| 3×2 | 3 | 524px | 6 | 是 |
| 1×1 | 1 | 1055px | 1 | 是 |
| 4×3 | 4 | 524px | 8（全部） | 否 |

行高按"每屏行数"反算：`(可用高度 - 行间距) / 每屏行数`，所以每屏正好填满。必须显式写 `grid-template-rows: repeat(rows, Xpx)`——只定义一行靠 `auto-rows` 会让多出来的行塌陷成 1px（踩过）。

### 中间大 · 右侧小窗（聚焦布局）

「布局」下拉里多了一个 **`中间大 · 右侧小窗`**：左边一块大画面，**右边只有一列小窗**，**点哪个小窗，哪个就换到中间播**。

| 规则 | 具体 |
| --- | --- |
| 主画面 | 占左边，宽度 = 网格宽 - 小窗列宽；**高度钉死成可见高度**，右侧滚动时它不动 |
| 小窗列 | **只有一列**，永远不分成两列/三列。宽度 = 网格宽 × 0.16（150~300px 之间），高度 = 宽 × 0.72 |
| 放不下怎么办 | 出**竖向滚动条**（滚动条只管右侧那一列，主画面用 `position: sticky` 钉在顶部，不会跟着滚走） |

### 小窗顶栏那排按钮（踩过的三个坑）

0. **全屏下点不到「关闭」**：全屏时顶栏是**绝对定位浮层**（`body.fs .tile:hover .tile-head`，原来 `z-index: 6`），而小窗画面上那层"点一下换到中间"的点击层也是 6。两者 z-index 相同，点击层在 DOM 里靠后 → 它盖住了顶栏，点「关闭」实际点到了点击层（于是那块被换到中间，而不是关掉）。修法：点击层降到 **5**，全屏顶栏抬到 **8**。
1. **按钮跑到左边去了**：一开始为了给按钮腾地方，把小窗顶栏的标题 `display:none` 了——可那个标题是 `flex: 1 1 auto` 的**弹性占位**，一去掉，按钮就从左边紧挨着编号排，右边空一大块。改成 `visibility: hidden`（占位留着、字不显示），按钮就重新贴右。
2. **列宽拖到最窄时"关闭"被裁掉**：小窗顶栏内容的实测最小宽度是 206px（编号 16 + 开始 46 + 音量 40 + 静音/放大/刷新/关闭 各 20 + 间距 padding），比原来的下限 120px 大，所以拖窄以后最后一个按钮会被 `.tile` 的 `overflow:hidden` 切掉。现在小窗里的按钮压紧（`.act` 20px、音量条 40px），下限抬到 212px。

### 聚焦布局里也能拖

按住小窗的顶栏（标题那一行）拖，两种落点：

| 拖到哪 | 结果 |
| --- | --- |
| 右侧小窗之间上下拖 | **调顺序**：其它小窗用 FLIP 让位，松手顺序就定下来（跟着房间列表一起存） |
| 拖到大画面上 | 大画面高亮成粉色、角标变成「主画面 · 松手换到这里」，**松手就换到中间** |
| 把大画面拖到某个小窗上 | **互换**：那块小窗换到中间，原来的大窗口回到它的位置 |

跟九宫格布局同一套实现：只改 Map 顺序 / `grid-column`、`grid-row`、`transform`，**一个 DOM 节点都不移动**，所以拖动全程 `webview` 不重载（实测 guest id 2/3/4/5 一动没动）。

其余两点说明：

- 小窗上面那层点击层会挡住页面内的点击（小窗里点不动弹幕按钮之类）。要操作某个房间，先点它换到中间（或者拖过去）
- 聚焦布局里不支持"整块拖到屏幕外再滚"的换位：右侧只有一列，靠上下拖就够

## 拖动瓦片换位置（排序）

**按住瓦片顶栏（标题那一行）拖**，把这块拖到别的格子上，松手就换位；拖动中那一块半透明、指针变爪子，其它瓦片实时让位。位置会**跟着房间列表一起存**，重启还是你排好的顺序。

实现上有两个刻意的选择：

| 做法 | 为什么 |
| --- | --- |
| **只改 CSS `order` + 内部 Map 顺序，绝不把 `<webview>` 节点从 DOM 里挪走** | `<webview>`（等于一个 OOPIF）一旦被父节点重新插入就会**重新加载**：画面重来一遍，正在录制的房间当场断流。所以"移动"是纯 CSS 排序，guest 进程一个都不动 |
| 拖动时盖一层全屏 `#drag-shield` | 指针划到视频区上方时，事件本来会被 guest 页面吃掉（`pointermove`/`pointerup` 收不到，拖到一半就没反应了）。盖一层透明盾牌把整页事件留在自己进程里 |

### 怎么做到"丝滑"的

第一版是"指针一动就 `order` 重排"，于是画面是一格一格**跳**过去，而且高回报率鼠标下一帧能跳好几次。现在改成三件事：

| 做法 | 为什么 |
| --- | --- |
| 被拖的那块用 **`transform: translate()` 一直贴着指针**（不是靠布局跳格） | 视觉上始终是"手里攥着这一块"，跟手。抓取点按下的位置也算进去了，按下不会"跳一下" |
| 其它瓦片换位用 **FLIP 补间**（先量旧位置 → 换完立刻反着 `translate` 回去 → 过渡到 0，170ms） | CSS `order` 本身不可过渡，直接换会"啪"地跳。FLIP 让它们**滑**过去 |
| **rAF 合并 + 10px 滞回** | 一帧只算一次位移；指针没挪够 10px 不重新判位，避免在两格之间来回抽搐 |
| 拖到网格上下边缘 56px 内 **自动滚动**（最多 18px/帧） | 瓦片多到要滚动时（比如 1×1 布局开 4 个），否则拖不到屏幕外的格子 |
| 拖动过程中**不落盘**，松手才写 `state.json` | 每帧一次 IPC + 写文件纯属浪费 |

细节（都已实测）：

- 顶栏上按下**不动**（移动 < 4px）什么都不变 → 双击放大、点按钮、拖音量条照旧
- 拖完紧跟的一次 click 会被吞掉（400ms 内），否则"拖完手一松"会顺手把瓦片放大
- 松手时那块会从"手里的位置"**滑回它现在所在的格子**（同一条缓动曲线），不会瞬移
- 拖完编号（左上角 `1 2 3 …`）立即重排，顺序在 350ms 后写进 `state.json`
- 单间放大（`⤢` / 双击）状态下不响应拖动——那时只显示一块，拖动没意义

验证（4 个真直播间同时播 1080p，脚本派发 pointerdown/move/up 模拟拖动）：

```
拖动前    order: r1=0 r2=1 r3=2 r4=3   位置: (6,137) (796,137) (6,525) (796,525)
按下不动  → 完全不变（afterClick 与 before 相同）
拖动中    被拖那块 transform=translate(-11px, 2px)，实际渲染位置 (x) 与"指针位置"差 1px（跟手）
          其它 3 块 style.transition 已挂上（FLIP 在滑）
拖完      order: r3=0 r4=1 r1=2 r2=3，编号 1/2/3/4 同步，残留 transform/transition = 0

## 隐藏顶部工具栏

顶部其实是**两条**：`#bar`（品牌 + 监控/观看 tab）和视图内的 `.row`（直播号输入、登录、全静音、画质、只看画面、弹幕面板、礼物、⚙ 录制选项、停止录制、全屏、录窗口…）。两者一起隐藏才算真的干净：

| 状态 | #bar | .row | 网格高度 |
| --- | --- | --- | --- |
| 正常 | flex | flex | 893 |
| 点工具栏右侧 **▴** 收起 | none | none | **986** |
| 再点右上角 **▾** 展开 | flex | flex | 893 |
| 全屏 | none | none | **1067** |
| 全屏时鼠标顶到屏幕最上沿停一下 | 两条以浮层出现（不挤压画面） | | 1067 |

手动收起状态**只在本次运行有效**，不跨重启记住；而且**退出全屏时会自动恢复工具栏**——否则"之前收起过 + 又进了全屏"，退出后看起来就是工具栏凭空消失。

另外有个兜底快捷键 **`Ctrl+Shift+H`**：任何状态下都能切换工具栏显隐（焦点在抖音画面里也有效），万一找不到 ▾ 就用它。

两个容易踩的细节（都已修）：

- 浮出后判断"鼠标是否还在工具栏上"用的是**两条的实际高度**（`#bar` + `.row` 的 bottom），不是固定 56px——否则鼠标一移到第二行的搜索框就被判成"离开"，工具栏当场收起、没法输入。
- **焦点在输入框里时完全不收起**（`focusin` 锁住、`focusout` 才释放），输入过程中不会被自动隐藏打断。

手动收起状态记在 localStorage，下次启动沿用；它和全屏互不依赖，F11 不生效的机器也能用箭头得到满屏画面。

## 全屏观看

工具栏「全屏」按钮或按 **F11** 进入全屏。全屏下做到**顶部零按钮**：

- 顶部工具栏整条收起（`display:none`）；**鼠标移到屏幕最顶部停 500ms** 才浮出，移开 500ms 自动收起，快速掠过不会误弹
- 工具栏浮出后有**双重收起保险**：鼠标离开工具栏边界 500ms 收起；另有 4 秒自动收起兜底——因为鼠标移进视频区后事件会被 `<webview>` 吃掉，只靠 `mousemove` 判断会让工具栏卡在顶部不动
- 每个瓦片的标题栏（录制/静音/关闭）也收起，鼠标移到某个瓦片上才浮出那一个
- **左上角常驻主播名**（只显示名字，去掉"的抖音直播间"后缀），保证全屏也能一眼看出哪个格子是谁
- 顶部提示文字 3.5 秒后自动淡出
- 实测瓦片尺寸从 839×438 变成 845×501

**Esc 或 F11 退出**（Esc 有优先级：全屏时先退全屏，未全屏时才取消单间放大）。

F11/Esc 的按键拦截放在主进程的 `before-input-event` 里，并且**主窗口和每个 `<webview>` guest 都挂**——因为焦点在抖音画面里时，渲染层 `window` 上的 `keydown` 收不到按键（会被 guest 页面吃掉），这是 F11 之前"按了没反应"的原因。另外渲染层每秒向主进程核对一次真实全屏状态，事件漏了也会在 1 秒内自愈。

## 监控台（探测谁在播）

顶部两个 tab：**监控** 和 **观看**。

「监控」页维护一个直播间地址池，用方形卡片展示，自动探测是否在播；勾选后点「查看选中直播」就把它们开到「观看」页。状态变化只体现在卡片上，**不弹系统通知**（按需求移除）。

**地址支持**：直播间号（`460102249360`）、`live.douyin.com/xxx`、分享短链 `v.douyin.com/xxx`（会自动跟跳转解析，非直播间的短链会被拒绝）。解析器和「观看」页的输入框是**同一个**（`room:resolve`），两边行为完全一致，详见「[两个"添加"入口](#两个添加入口观看页--监控页现在完全一致)」。

**重复添加会明确提示**（原来是静静失败，看不出发生了什么）：

- 渲染层先自己判一次重（房间号 + 归一化 URL 两种写法都认：`…/612630333230`、`…/612630333230/`、`…/612630333230?enter_from=share` 是同一个房间），命中就立刻提示，不走网络

- 短链（`v.douyin.com/xxx`）本地判断看不穿，所以主进程解析完再去重时也会带上房间名返回，界面同样提示 + 闪卡片

提交新房间号 999000111222    → 「已加入监控列表，稍后会自动探测是否在播」[ok]，watchers 3
```

**探测是怎么做的**（三条路里只有这条通）：

| 方案 | 结果 |
| --- | --- |
| 直接抓直播页 HTML 解析状态 | ❌ HTML 是空壳，1.2MB 里没有任何状态字段，`<title>` 也没有 |
| 直连 `webcast/room/web/enter` 接口 | ❌ 返回 200 但 0 字节，需要 `a_bogus` 签名 |
| **隐藏窗口加载页面 + 屏蔽媒体流 + 读 DOM** | ✅ 采用 |

细节：常驻一个隐藏 `BrowserWindow`，串行处理队列（不并发开 N 个页面）；`webRequest` 拦掉 `flv/m3u8/ts/mp4` 等媒体请求——页面照常渲染出状态，但不下载视频流；用独立 partition（`persist:probe`）不带登录态，避免探测影响账号的"当前直播间"。

判定信号（实测标定过）：

- **「直播已结束」这类文案最可靠**——标题在主播下播后**完全不变**，只靠标题必然把已结束的房间误报成在播（实测 `live.douyin.com/101326782951` 已结束，标题仍是「dota直播卓一航的抖音直播间」）
- 标题里的 `某某的抖音直播间` 只能作为辅助信号，且要排除假标题：`/1` 的标题是「**账号已注销**的抖音直播间」
- 正文出现 `直播已结束/主播已下播/未开播/直播间不存在` → offline（优先级高于标题）
- 页面 JS 卡住时用窗口标题兜底

> ⚠️ 实测结论（重要）：**标题不能用来证明"在播"**。`dota罗导`（435606905090）在网页上显示未开播，但标题仍是「dota罗导的抖音直播间」，旧的"标题兜底"逻辑把它误报成"在播/刚开播"，用户实测发现了这个问题。
>
> 现在的判定顺序：验证码 → blocked；正文有「直播已结束」→ offline；**有正在解码的视频（`videoWidth>0` 且未暂停）→ live**；有视频但暂停 → offline；**什么都读不到 → unknown（保留上次判定并标「⚠ 未确认」）**。
>
> 之所以会"什么都读不到"：已结束的房间页会把渲染进程主线程卡死。实测对照——`example.com` 1.2 秒读出 DOM；在播直播间能读；已结束直播间无论隐藏窗口、屏幕外可见窗口、还是应用内可见瓦片，`executeJavaScript` 都超时（73–110 秒无响应，清空分区存储也无效）。
>
> 试过但**不可靠**的两条 JS-free 判据（都留在代码里仅作诊断）：① 统计媒体（flv/m3u8）请求数——直播流是长连接只发一次，三个房间数值完全一样分不开；② 帧差（`capturePage` 两次对比）——单次能分开（在播 4–35% / 已结束 0–0.1%），但复用窗口里等待久一点，已结束页面的广告/动画会把帧差抬到 38–43%，不稳。
>
> ✅ **已改成用 CDP 量媒体流量判活**（`Network.dataReceived`，主进程侧，不受页面主线程影响）。实测对照：
>
> | 房间 | 媒体请求 | 6 秒流量 |
> | --- | --- | --- |
> | `dota罗导`（实际未开播） | 无 pull-flv | 0 字节（只有 199KB 页面静态资源） |
> | `101326782951`（已结束） | 无 pull-flv | 0 字节 |
> | `338647466220`（在播） | pull-flv ×3 | **4.3 MB** |
>
> 阈值取 300KB。关键实现细节：**CDP 必须在导航之前挂上并 await 到 `Network.enable` 生效**，否则直播流那条长连接已经建立，抓不到它（踩过）。

实测：`460102249360 → live(dota pk4丶)`，`999999999999 → offline`，`1 → offline(账号已注销)`，单次探测 6–10 秒。

**成本与频率**：每个地址每次探测都是一次整页加载（6–10 秒）。默认**每个房间 120 秒探一次**，32 个房间轮一遍约 1 小时；被验证码拦后按 30min → 1h → 2h → 4h 指数退避。地址多了要么拉长间隔，要么减少监控数量。

### 打开观看会反刷监控状态（瓦片 → 监控）

每个打开的瓦片在主进程挂了一个 CDP 流量计量器（`Network.dataReceived`），用"到底有没有在拉流"这个事实去纠正监控页。

| 时机 | 行为 |
| --- | --- |
| **打开后约 18 秒** | 一次快速判定：等过页面加载突发（实测前 10 秒能到 3–8MB/s），再取 6 秒的流量算速率。**只用来尽快报「在播」，绝不报「停播」** |
| 之后每 15 秒 | 长窗口平均（最长 90 秒）≥ 150 KB/s → 在播；低于阈值时再读一次页面里的 `<video>`，确认视频确实没在放，连续 2 次才判未开播 |
| 窗口不足 20 秒 | 不下判断（刚打开时全是加载突发） |

实测：把 `dota炸天`（实际没播、监控里状态停留在一小时前）打开后——

```
+10 秒  tile meter quick verdict 219181511666 0KB/s offline
        status corrected by tile 219181511666 offline
+12 秒  监控卡片已变成未开播（source=tile）
```

这样即使探测窗口读不到页面状态，只要你打开看过一眼，监控页就会自动对上。被纠正的卡片状态来源记为 `tile`。

#### ⚠️ 修过的坑：在播的房间被判「未开播」（用户实测 `dota老花一打九`）

早期版本用**瞬时 6 秒窗口**判活，结果把正在看的在播房间判成了未开播。原因是抖音播放器**不是匀速拉流**：它一次拉一大块（实测单块累计到 **89MB**）然后播一段，这段时间 CDP 计数就是 0。同一房间同一时刻的读数：

| 采样窗口 | 计数 | 旧逻辑判定 |
| --- | --- | --- |
| +18~+24 秒（6 秒） | 0 KB/s | ❌ **offline** ← 卡片变未开播 |
| +14~+29 秒（15 秒） | 678 KB/s | live |

而与此同时画面一直在播——`<video>` 的 `currentTime` 每 15 秒稳定前进（10→25→40→…→145 秒），`videoWidth=1920`。所以「没流量」是**采样窗口的错觉**，不是房间停播。

顺带排除了一个猜想：不是 worker / 子 target 把流量吞了。用 `Target.setAutoAttach({flatten:true})` 挂上子会话后，父会话与子会话的字节数**完全相等**（674/3024/773 KB/s 对 674/3024/773 KB/s），页面里确实有 worker（`service_worker`、`blob:` worker、`worklet`），但它们没有额外流量。

现在的规则是「流量 + 视频状态」双判据：

| 证据 | 判定 |
| --- | --- |
| 90 秒长窗口平均 ≥ 150 KB/s | 在播（铁证，不用读页面） |
| 流量低，但 `currentTime` 在前进 / 未暂停 / 有画面 | **在播**（这正是上面那种情况） |
| 流量低 + 视频没在放（`paused` / `videoWidth=0` / `currentTime` 卡住），连续 2 次 | 未开播 |
| 流量低 + 读不到页面（已结束的房间主线程会卡死，4 秒超时）连续 2 次 | 未开播（日志标注 `js-timeout(页面卡死)`） |
| 只播着一个 `.mp4` 广告片 | 未开播（已结束页面会循环播 199KB 广告，`currentSrc` 是 `xxx.mp4`；直播流走 MSE，`currentSrc` 为空） |

实测对照（两个房间同时开着，跑 150 秒）：

```
612630333230  在播  avg 0KB/s  video=playing@145s/1920  → 一直 live，low#0 从未累积
435606905090  停播  avg 0KB/s  video=unreadable          → verdict offline  js-timeout(页面卡死)
485185918272  在播  avg 3105KB/s                        → live
338647466220  在播  avg 739KB/s                         → live
```

探测窗口（`probe.js`）也有同一处隐患，一起改了：原来「流量不到 300KB 就是 offline」是硬结论，6 秒窗口落在拉流间隙就会误报。现在先看流量，够量 → live；不够量再看页面里的视频是否在放直播流（排除广告 mp4）→ live；都不成立才 offline。

### 卡片排版（尺寸 / 不重叠）

卡片是正方形的（`aspect-ratio: 1/1`），高度由列宽推出来。这里踩过一个坑：`#cards` 是 `display: grid` 且高度被 flex 约束住，而**`aspect-ratio` 推出来的高度不算"内容"**，于是 `auto` 行会按"内容高度≈0"被压扁，再平均分掉容器剩余高度——卡片本身 225px 高，格子却只有 155px，结果**每一行的卡片都压在下一行上**：

| 窗口宽度 | 格子行高 | 卡片实际高度 | 行与行重叠 |
| --- | --- | --- | --- |
| 1686 | 154.7px | 227px | **63px** |
| 1186 | 75.3px | 222px | **137px** |
| 966 | 52.2px | 225px | **163px** |

修法是 `grid-auto-rows: max-content`（让行按卡片真实高度走，实测三种宽度重叠都变 0，容器正常滚动）。顺带调了两处：

- 列最小宽度 `200px → 240px`、间距 `10px → 12px`，1686 宽下是 6 列 × 264px（原来 7 列 × 225px），标题不再挤在一起
- 卡片顶栏重排：**勾选 · ★ · 打开/移除（hover 显形） · 状态角标** 现在是一行 flex，全在卡片顶部

顶栏改动的原因：`打开 / 移除` 原来浮在封面垂直中央，`状态角标 / ★ / 勾选` 各自绝对定位在三个角，位置靠硬编码坐标拼出来（`top:8 right:8`、`top:8 left:36`），加一个控件就要重算一次。现在统一进 `.card-top`（`position:absolute; top/left/right:8px; display:flex; gap:6px`），`打开/移除` 用 `margin-left:auto` 靠右、角标固定在右上角。实测 264px 卡：勾选 `21–43`、★ `49–71`、打开/移除 `132–215`、角标 `221–268`，相邻不重叠、全部落在卡内（`worstOverlap: 0`、`allInsideCard: true`），264px/308px 两种尺寸都成立。按钮隐藏时 `pointer-events: none`，不挡点击。

### 状态过期提示

32 个房间每 120 秒探一个，一轮要 1 小时多——所以列表里的状态**可能很旧**。超过 20 分钟没探过的卡片会：

- 底部署名追加 `◦ 状态可能过期`
- 卡片边框变成**虚线**
- "直播中"角标从鲜绿降级为灰绿 + 虚线描边

> 这就是 `dota炸天` 那次的成因：它最后一次检测是 13:10，而当时已经 14:28（一小时前）。判定逻辑没错，是**数据太旧**。打开看一眼就能立刻校准。

| 反馈 | 表现 |
| --- | --- |
| **正在探测哪一张卡** | 该卡片边框变**橙色并呼吸闪动**，顶部还有一条扫光进度条（`.card.probing`），实测同时只会有一张亮 |

| **底部统计栏** | 监控页底部一行：`共 32 个 · 在播 5 · 未开播 26 · 未检测 1 · ★ 4 · ⚠ 未确认 2 · 已检测 32/32 · 最后检测 1 分钟前`，有被拦截时整行变橙色 |
| 探测中再点「检测选中」 | 不再被拒绝，会**排队**并在状态栏提示"已排队 N 个房间，等当前这一轮结束就开始"，当前轮结束后自动执行 |
| 读不到状态时 | 卡片显示上次判定 + `⚠ 未确认`，不会凭空报"在播" |

### 卡片顺序（不跳）

早期版本会**自动把在播的排到最前**，而排序的兜底键又是"最后检测时间"——每轮探测都在改这个字段，于是卡片会自己挪位置，想点的那张刚伸手就跑了。

现在工具栏有「排序」下拉，默认 **添加顺序**：

| 选项 | 规则 | 会不会自己跳 |
| --- | --- | --- |
| **添加顺序**（默认） | 只按加入监控的先后排 | ❌ 状态怎么变、探多少次都不动 |
| 在播优先 | ★ 特别关注 → 在播 → 未确认 → 出错 → 未开播，同级按添加顺序 | ✅ 状态变化时会重排（这是它存在的意义） |
| 按名字 | 按主播名/标题 `localeCompare`（中文按拼音） | ❌ |
| 最近检测 | 刚探完的排最前 | ✅ 每轮探测后重排 |

实现要点：`sortCards()` 里**每种模式的最后一个比较键都是添加顺序**（`watcher.id` 是主进程自增序号，永不变），所以同一份数据的排序结果是确定且可重复的，不再依赖 `checkedAt` 这种每次都变的字段当兜底。选择结果存在 `localStorage` 的 `pr.monSort`。

### 已验证可用的替代数据源：关键词搜索页

`https://www.douyin.com/jingxuan/search/<关键词>?type=live`（例：`dota 直播`）在**登录态**下能正常渲染且 JS 可读——实测一次加载 + 滚动抓到 **79 个在播房间**（`show:false` 隐藏窗口也能读，和直播间页面完全不同）。**匿名访问返回 0 条**，所以必须用已登录 session。

## 它是怎么做到的

直播服务端判定"你还在这个房间里"，靠客户端上报的 **进房事件 + 周期心跳**，状态记在 `(uid, room_id)` 维度上。所以只要每个房间各有一条独立的客户端连接持续心跳，**画面层面**同一账号同时待在多个房间是可行的。

本工具的做法：

1. 所有房间窗口共用同一个 session partition（`persist:douyin`）→ **扫码登录一次，登录态对全部房间同时生效**，确实是同一个账号，不是多个小号。
2. 每个房间是一个独立的 `<webview>`（独立渲染进程）→ 各自维持进房和心跳，**互不覆盖、不会互相踢出**。
3. 窗口失焦也继续解码：关掉了后台节流（`disable-background-timer-throttling` 等），否则后台房间会被降频甚至挂断。

> ⚠️ **重要修正（实测后）**：抖音**确实**维护"这个账号当前在哪个直播间"，比最初的判断更严格。多个房间同时开着时，页面会弹出一条瞬时提示 **「账号已在其他地方进入直播间」**。它不阻断播放（实测三路画面一直在播），但它说明"账号在场"这件事**只算一个房间**。详见下面「多房间的真实代价」。

### 两个"添加"入口（观看页 / 监控页）现在完全一致

原来两边各写了一套解析，行为不一样。现在已经统一：两个输入框都通过主进程的同一个解析器（IPC `room:resolve`，实现是 `watchers.js` 的 `resolveRoomInput`），区别只剩下"加进来以后干什么"。

| 输入 | 结果（两边一致） |
| --- | --- |
| `612630333230` | ✅ 认成房间号 |
| `https://live.douyin.com/612630333230`、带末尾斜杠、带 `?enter_from=share` | ✅ 都归一成 `https://live.douyin.com/612630333230` |
| `live.douyin.com/612630333230`（没 scheme） | ✅ |
| 分享文案（`7- 看看这个 #在抖音看直播 https://live… 复制此链接`） | ✅ 从文案里抠出链接 |
| `https://v.douyin.com/xxx`、`v.douyin.com/xxx` | ✅ 会**跟一次跳转**解析成真实房间；不是直播间的短链明确拒绝 |
| 主页 / 搜索页 / 随便一个网址 / `javascript:` / 乱字符 | ❌ `无法识别的地址（要直播间号、live.douyin.com 链接或分享短链）` |

| | 观看页「添加」 | 监控页「添加」 |
| --- | --- | --- |
| 加进来是什么 | 一块**瓦片**（立刻开始播） | 一张**监控卡片**（立刻探一次在播状态，不打开画面） |
| 判重范围 | 已打开的瓦片（同一房间只开一块，防声音叠两遍） | 监控列表（同一房间只留一张卡） |
| 数量上限 | 12 块瓦片 | 不限 |
| 失败提示 | 输入框闪红 + 状态栏红字 | 输入框闪红 + 状态栏红字（重复时黄字 + 闪已有卡片） |

修掉的两个真问题（都是"两套解析"的后果）：

- `https://v.douyin.com/xxx`（从**地址栏**复制的那种，带 scheme）在监控页永远报 `无法识别的地址`——因为旧代码的所有分支都在"去掉 scheme 的候选串"上匹配，短链解析那一段根本走不到；而观看页会把它**当成一个瓦片直接打开**。
- `v.douyin.com/xxx`（不带 scheme，分享文案里通常长这样）在观看页直接被拒——渲染层那份正则少了 `v\.` 这一支。

还有一个副作用一并修了：观看页现在存的是**归一化后的房间地址**，所以"短链 + 房间号"给的同一个房间不会再开成两块瓦片（以前 `bareUrl` 拿短链当 key，防回声的判重会失效）。

实测（沙箱，同一批 11 种输入、两个入口各跑一遍）：

```
房间号 / live 链接（斜杠·query）/ 无 scheme / 分享文案  → 两边都 ok，url 与 roomId 完全相同
https://v.douyin.com/iRNBho6u/  → 两边都「短链解析失败」（旧版：监控页"无法识别的地址"，观看页直接开瓦片）
v.douyin.com/iRNBho6u/          → 两边都「短链解析失败」（旧版：观看页"静默拒绝"）
douyin 主页 / example.com / javascript: / abc → 两边都拒绝
观看页重复提交（?enter_from=share 变体）→ 「这个直播间已经在看了…」+ 闪瓦片，瓦片数不变
观看页新增房间 → 瓦片 +1，状态栏清空（文字和颜色都清，不会留一行红字）
```

### 关窗口 / 重新启动的行为（"关掉后再点 start.bat 看不到界面" 已修）

现象：`start.bat` 起来用了一次，关掉窗口，再点 `start.bat` 什么都没发生，看不到界面。

原因有两层，都跟"主窗口关掉之后进程并没真退出"有关：

| 层 | 真相 |
| --- | --- |
| 1 | **探测用的隐藏窗口一直活着**（`BrowserWindow({show:false})`，走轮询探测时创建）。Electron 的 `window-all-closed` 是"**所有**窗口都关了"才触发，所以主窗口关掉后这个事件根本不来，进程一直挂着 |
| 2 | 那个僵尸进程仍然握着**单实例锁**。再点 `start.bat`，新进程 `requestSingleInstanceLock()` 失败 → 立刻 `app.quit()`；旧进程收到 `second-instance` 事件，但它的 `win` 已经被销毁了 → 原来的代码只做 `if (win && !win.isDestroyed()) win.show()`，于是**什么都不发生** |

修法（三条一起，缺一条都会漏）：

1. **主窗口 `closed` 后直接 `app.quit()`**：不再指望 `window-all-closed`（隐藏的探测/录制窗口不该成为"退不出去"的理由）。
2. **`second-instance` 里如果发现没有窗口，就原地重建一个**：万一进程还在（例如正在合并分段），第二次启动也会立刻出现界面，而不是静默退出。
3. **收尾有硬超时**：`before-quit` 等 `recorder.dispose()` 最多等 3 分钟，超时 `app.exit(0)` —— 绝不让一个卡住的 ffmpeg 永久占着单实例锁。

另外顺手改了"正在录制时关窗口"的体验：现在会**拦住关闭**，状态栏显示 **`正在保存录制（合并分段）… 完成会自动关闭窗口`**，收尾完才真正关。以前是窗口先没了、进程还在后台合并，用户以为程序挂了（也是上面僵尸状态的来源）。

实测（沙箱，录制中直接 `window.close()`）：

```
关窗口前  状态栏「● 录制中 1 路(流) 第1段 00:14」
关窗口    window close: finalize recordings first 1
          main window closed -> quit
          before-quit
1 秒后    进程已退出（ffmpeg=0），没有残留
输出      4 个分段合并成 关窗口收尾测试_….mp4（2.58 MB）—— 录制没丢
再来一次  同一个数据目录重新启动 → 进程正常存活，页面 file:///…/renderer/index.html 出现（界面正常）
不录制的关闭  同样 `main window closed -> quit` → `before-quit` → 立刻退出
```

### 虎牙（huya.com）支持情况

从这一版开始，除了抖音，也能加虎牙直播间：

```
https://www.huya.com/mingjie      ← 主播主页名
www.huya.com/mingjie
huya.com/660000                   ← 数字房间号也行
```

工具栏新增 **「登录虎牙」**（和「登录抖音」并排）：登录态落在同一个共享 partition，瓦片里的虎牙页面直接带上，重启也不丢。

| 能力 | 状态 | 实测数据 |
| --- | --- | --- |
| 添加 / 观看 | ✅ 可用 | 匿名就能播（`800×450`，标题 `冥界官方直播间-DOTA1-虎牙直播`） |
| 画质 | ✅ 登录后升一档 | **未登录 800×450 → 登录后 1280×720**（同一个瓦片重载后连采三次都是 720p，cookie 里出现 yyuid/udb）；页面没登录时就是低一档，所以"画质不好"确实是没登录 |
| 声音 | ✅ 只留主画面 | 虎牙页面同时有 **2 个 `<video>`**（主画面 + 竖屏推荐浮窗），现在除了主画面其余一律强制静音 —— 否则就是两路声音混着响 |
| 监控探测 | ✅ 可用 | 虎牙页面上没有「直播中/未开播」文案，靠"video 在播 + 流量"判断；探测窗体一直是静音的 |
| **录制** | ✅ **直录流 1080p** | `h264 1920×1080 30fps + aac 立体声 ~8.5 Mbps`，`-c copy` 不重编码；见下 |

**虎牙直录流是怎么打通的**（思路移植自 [DouyinLiveRecorder](https://github.com/ihmily/DouyinLiveRecorder)，只搬"取地址 + 改参数"这一小段，不引入 Python 依赖）：

先踩过的坑——页面里 `window.hyPlayerConfig` 那份签名地址，出了播放器环境就拉不动：

```
AL  flv  403 Forbidden
TX  flv  连上吐 1.46 MB 就 EOF（约 0.6 秒）
HS  hls  能连，2.8 MB 后同样 EOF（3~4 秒，Failed to reload playlist 0）
加 -reconnect 硬续 → Packet is missing PTS / Unable to seek，录出来花屏
```

正确路径（本版实现，`main.js` 的 `huyaStreamCandidates()`）：

1. **拿到 `profileRoom`**（接口要的是这个，不是房间号）：
   - 优先**从页面里读**：渲染层执行 `window.TT_ROOM_DATA.profileRoom`（`huya.com/wuhushenkp` → `353322`）。
     这一条必须走页面，因为很多房间的 HTML 里**已经没有** `ProfileRoom` 字段了（实测 `wuhushenkp` 的 HTML 58KB，一个都没有）。
   - 兜底才用 HTML 正则 `ProfileRoom":(\d+)`，或者 URL 本身就是数字。
2. **走微信小程序接口拿流信息**：
   `https://mp.huya.com/cache.php?m=Live&do=profileRoom&roomid=<profileRoom>&showSecret=1`，
   带 iOS UA + `xweb_xhr: 1` + 小程序 referer。
   （传房间号 `1016578758` 会返回空对象，必须传 `profileRoom`。）
3. 取 `data.stream.baseSteamInfoList[]`，按 **TX > HW > HS > AL** 优先级拼 `flv` / `m3u8` 地址。
4. **把 App 客户端参数改写成网页客户端**（关键一步）：
   `ctype=tars_mp → ctype=huya_webh5`、`fs=bhct → fs=bgct`，并统一走 https。

改完实测（房间 `mingjie` / 194501）连续拉 45 秒不断（43.8 MB / 约 7.8 Mbps）；成片：

```
HUYA-DLR-TEST_….mp4   15.88 MB  15.6s
h264 1920×1080 30fps + aac 2ch   平均 8.52 Mbps
```

### 但虎牙**房间之间不一样**（同一套地址，有的能长拉、有的只吐几秒）

| 房间 | 分辨率 | 用同一套方法实测 |
| --- | --- | --- |
| `mingjie`（冥界，DOTA1） | 1920×1080 | ✅ 连续 45 秒不断，稳定直录 |
| `wuhushenkp`（微竞-芜湖神，英雄联盟） | **2560×1440** | ⚠️ 三条线路 × 两种签名（原样 / 按 md5 重算 anti-code）都只吐 **1~5 秒**就断（403 或 EOF 或"连着不吐数据"） |

也就是说：**直录流能不能长拉，取决于房间/码率链路**，不是我们代码的 bug。所以录制逻辑做成两级：

1. **先试直录流**（1080p 原画，`-c copy`）；
2. 开录后 5 秒起每 2 秒检查一次：**如果这次直录已经自己停了**（断流且换完所有线路仍失败），就**自动切成屏幕录制**：
   把这块画面放大单间，状态栏明说
   `虎牙这个房间的直录流只维持了 N 秒就断，已自动改成屏幕录制（画面会放大）`。
   每块瓦片只自动兜底一次，不会来回折腾。

实测（`wuhushenkp`，点一次录制）：

```
t+0s    ● 录制中 1 路(流) 第1段 00:00      ← 先试直录
t+12s   ● 录制中 1 路(流) 第1段 00:12      ← 直录跑了一段
t+18s   ● 录制中 1 路(屏) 第1段 00:02      ← 直录被切 → 自动改屏幕录制（画面已放大）
t+36s   ● 录制中 1 路(屏) 第1段 00:20      ← 之后再没断
输出    微竞…_082754.mp4（直录那一段 4.36 MB） + 微竞…_082809.mp4（屏录 0.67 MB）
```

> 注意会留下**两个文件**（直录那一段 + 屏录那一段），因为两种模式是两次录制会话；需要合成一个就用「剪辑」页签多选合并。

- `anti-code` 大约 **2 分钟**有效 → 渲染层每 **60 秒**自动续一次（`reportHuyaStream`），开录前再强制续一次；
  断流重连走的是同一份新鲜地址，所以不会像以前那样"录两分钟就断"。
- 取流用 Node 自带的 `fetch`（undici）而不是 Electron 的 `net.fetch`：后者走默认 session，会被应用里的
  webRequest 规则拦成 `net::ERR_BLOCKED_BY_CLIENT`（实测踩过）。
- 直录流支持**多 CDN 候选 + 自动换线**（某条线路 403 或只吐半秒会自动试下一条，同一条线路只试一次），抖音也受益。
- 万一接口取不到（房间没播 / 接口异常），才会退化成屏幕录制，并在状态栏说明原因。

还没做的：虎牙的**纯净模式**（页面结构完全不同，右侧聊天/左侧榜单/悬浮推荐位要单独适配）、虎牙网页端画质**切档**
（画质菜单是画在 canvas 里的，DOM 点不到；不过录制侧已经是 1080p，不受影响）。

## 实测情况（本机验证过）

- 4 个真实直播间同时打开，全部 `paused:false`、`readyState:4`，间隔 15 秒连续采样时间轴仍在推进 —— 确实是多路同时播放，不是只挂着页面。
- **未登录也能看**，但原画只有 29 秒试看（页面提示「原画可试看29s，登录可无限畅享原画画质」），之后自动降画质继续播。登录后解除。
- 浏览器自动播放策略会随机把某几路停在暂停态（实测 4 间里有 2 间被停）。已内置**看门狗**：每 4 秒检查一次视频是否在播，被停就恢复播放，并把页面自身的 `video.muted` 同步成磁贴的静音状态（真正消音由 Chromium 层负责）。
- 房间列表/静音状态在每次改动后 350ms 落盘，强杀进程也不丢；重启自动恢复。

## 多房间的真实代价：账号只算一个房间

登录后实测（3 个真实直播间同时开，间隔 14 秒采样三轮）：

| 采样 | 房间 1 | 房间 2 | 房间 3 | 播放状态 |
| --- | --- | --- | --- | --- |
| 12s | 无 | 无 | 无 | 三路 `paused:false` |
| 26s | 无 | 无 | **有提示** | 三路 `paused:false`，时间轴推进 |
| 40s | 无 | 无 | 有 | 三路 `paused:false` |

**这是服务端独占，不是客户端存储互斥**——做了一个隔离实验来证明：给每个房间分配独立 partition（各自 69 个 cookie 全部从主 session 复制过去，`logoutHint:false` 确认仍是登录态），localStorage / IndexedDB / BroadcastChannel 三者完全隔离，**提示照样出现**。所以隔离存储这条路走不通，不用再试。

实际表现（也是你操作时最容易困惑的点）：

- 提示是**瞬时 toast**，几秒后自己消失，所以不同时刻采样会撞到不同房间。
- **视频其实一直在播**，你看到的"不播放"是那层提示浮层盖住了画面。
- **所有权会随操作转移**：你点一下被提示的房间，它就重新抢到"当前直播间"，原来在播的房间反过来被提示。等于一圈里只有一个房间能"名正言顺"。

所以结论是：

- ✅ 能同时**看**多个房间（画面、弹幕都正常）
- ❌ 同一账号只有一个房间被算作"在场"：停留、亲密度、榜单、抽奖资格只认那一个
- ❌ 想让每个房间都算数，单账号做不到。只能多账号轮流进（违规，同设备多号易关联封号）或协议层伪造（风险更高）

### 两个缓解开关

| 开关 | 作用 | 代价 |
| --- | --- | --- |
| 磁贴上的「非当前房间」角标 | 自动识别那条提示，标出哪个房间不被算作在场（90 秒内不再出现才清掉，不会闪） | 无 |
| 工具栏「显示真实画面」（默认开） | 抖音在"账号已在别处"时会用一张静态封面图盖住仍在播放的视频；开启后自动揭开这层，真实画面就露出来了（每 4 秒复查，被盖回去会再揭） | 只是解决遮挡，**不改变**平台的在场统计；属于对页面 DOM 的干预 |

### 被盖住的假象（关键发现）

一开始我用 `video.paused` / `currentTime` 判断"在不在播"，结论是"三路都在播"——**这是错的**。改用**两帧像素比对**（同一房间隔 0.9 秒截两张图，算差异像素占比）后真相是：

| 房间 | 有无提示 | `paused` | 画面差异占比 |
| --- | --- | --- | --- |
| 房间1 | 有 | false | **0%**（完全静止） |
| 房间2 | 无 | false | 19.7% / 25.4%（真的在动） |
| 房间3 | 有 | false | **0%** |

视频元素确实在播、时间轴在走，但抖音在视频上面盖了一张静态封面图（IMG + 几层绝对定位 DIV），你看到的就是一张不动的图。

**揭盖有效**：把盖在视频中心区域、且不属于 video 自身的绝对定位元素 `visibility:hidden` 之后——

```
uncover 房间1 hidden:[IMG, DIV, DIV] → 帧差 0%   → 45.1%
uncover 房间3 hidden:[IMG, DIV, DIV] → 帧差 0%   → 6%
15 秒后复测：房间1 41.4% / 房间2 6% / 房间3 39%   ← 三路都在动
```

内置成开关后连续三轮实测（12s/26s/40s）三路帧差都大于 0：27.1→10.5→26.9、5.9→27.4→13.8、44.1→6.7→6.2。

## 画质

抖音默认给的是 **`960x540`（540p）**，实测 4 个房间全是这个分辨率——这就是"看着不清晰"的原因。它把清晰度选项（原画/蓝光/超清/高清/标清）渲染在 DOM 里，所以可以对目标档位直接派发点击事件来切换，不需要打开菜单。

实测：点击「原画」后四个房间全部 `960x540` → **`1920x1080`**。

现在加载后会自动切到工具栏选定的档位（默认原画），并且在页面加载完成后的前 6 次看门狗周期（约 24 秒）内反复补切——播放器重新初始化会把画质重置回去。下拉可选：原画 / 蓝光 / 超清 / 高清 / 标清 / 不干预。实测自动切换生效后，32 秒采样时四个房间都已是 `1920x1080`。

注意：

- 原画会显著吃掉带宽和 CPU，房间多的时候如果卡顿，退回「高清」或「超清」。
- 未登录时原画只有 29 秒试看，之后自动降档；要真原画得先扫码登录。

### 单个房间单独设画质（右键瓦片顶栏）

工具栏那个下拉是**全局默认**，所有没单独设过的房间跟着它。想给某一个房间单独降档（比如 12 路里只想让 2 个走原画），**在它的顶栏上点右键**，会弹出这个小菜单：

```
这个房间的画质 · Dota_My弟
  [x] 跟随全局（现在是「原画」）
  ─────────────
    原画 / 蓝光 / 超清 / 高清 / 标清 / 不干预
  ─────────────
  所有房间都用「原画」
```

- 覆盖值按房间存（`pr.prefs.qualities = { "room:920157546291": "高清" }`），重启还在
- 选完**立刻**推给那个页面（不等看门狗那一拍）
- 为什么放右键：小窗顶栏只有 212px 宽，再塞一个下拉会被裁掉；右键不占宽度
- 顶栏在**全屏下要悬停才出现**，所以全屏里先移上去再右键

实测：

## 只看画面（纯净模式）

需求是"只要视频，右侧弹幕栏、飘屏弹幕、底部礼物栏、页头都别要"。做法是沿 `video` 的祖先链往上走，**把每一层的兄弟节点全部 `display:none`**，再让视频 `position:fixed; inset:0; object-fit:contain` 铺满视口。这样不管抖音的 UI 有多少层、叫什么类名，只要它不是视频的祖先链就会被去掉。

实测（3 个真实直播间）：

| 指标 | 纯净模式前 | 纯净模式后 |
| --- | --- | --- |
| 页面可见文字长度 `bodyTextLen` | 数百~数千字 | **14** |
| 视频中心最上层元素 `centerIsVideo` | 常是覆盖层 DIV | **true**（就是 video 本身） |
| 三路画面帧差 | 12.8 / 20.1 / 9.2 | 仍然 12.8 / 20.1 / 9.2，都在动 |

关掉这个开关会**自动重载**房间，把页面恢复原样（被 hidden 的元素不会自己回来）。

## 弹幕 / 礼物

抖音自己的侧栏在 787×425 这种瓦片尺寸下**时有时无**（同一个房间不同时刻，DOM 里一会儿有弹幕列表、一会儿完全没有），所以不能指望它。

本工具的做法是**自己抓、自己渲染**：每 4 秒从弹幕容器里逐个子节点提取"昵称：内容"行和礼物类行（`送出/赠送/送了/投喂/加入了粉丝团/点亮了`），渲染在每个瓦片左下角的半透明面板里。纯净模式下侧栏虽然被藏了，但隐藏元素的文本仍可读取，所以面板照样工作。

实测礼物行（真实事件，不是造的数据）：

```
房间2  🎁 1钻小心心1钻赠送QQ  🎁 1钻人气票1钻赠送WW  🎁 9钻万圣快乐9钻赠送EE
房间3  🎁 30000钻嘉年华30000钻赠送  🎁 99钻送你糖果99钻赠送
```

### 四个开关

| 按钮 | 默认 | 作用 |
| --- | --- | --- |
| 只看画面 | 开 | 藏掉抖音所有 UI，只留视频铺满；关掉会自动重载恢复 |
| 弹幕面板 | 开 | 自渲染的聊天弹幕（默认左下角小面板），45 秒没新数据才隐藏 |
| **弹幕设置** | —— | 弹小菜单：**显示几行**（4/6/8/10/12）、**字号**（10~17px）、**贴哪个角**（左下/右下/左上/右上）。都记在 `pr.prefs` 里 |
| 礼物 | **关** | 是否在弹幕面板里也显示礼物信息（`🎁` 前缀）。默认过滤掉 |
| 显示真实画面 | 开 | 揭开抖音在"账号已在别处"时盖在视频上的静态封面 |

弹幕设置的实现：行数直接进 guest 脚本（`.slice(-N)` 决定抓最后几行），字号和位置走 `body` 上的 `dm-pos-*` 类 + CSS 变量 `--dm-font`，所以改一次全体瓦片立刻生效，不用重载页面。

实测（点「弹幕设置」→ 15px → 右下 → 12 行）：

```
菜单三段       显示几行 / 字号 / 贴哪个角，当前项打勾（8 行 / 11px / 左下）
改完           danmuLines=12  danmuFont=15  danmuPos=br
body           类 "dm-pos-br"，CSS 变量 --dm-font: 15px
面板实测        computed font-size: 15px；贴右下时右边距 8px、下边距 8px（改前是左下 8/8）
落盘           pr.prefs = { danmuLines: 12, danmuFont: 15, danmuPos: "br" }
```

### 一个技术坑：`display:none` 会丢文字

纯净模式第一版是把侧栏 `display:none`，结果弹幕面板直接空了——因为"昵称：内容"里的**冒号是 CSS 生成内容**，元素不渲染时 `textContent` 拿不到它，整行就被过滤掉了。

改法：文字密集的区域（`innerText` 长度 > 120 的面板）不用 `display:none`，而是 **`position:fixed; left:-30000px`** 挪出视口。它仍然处于渲染状态，文字（含生成内容）读得到，但你看不见。

实测四个房间同时都有弹幕，礼物行计数为 0（默认关）：`刘吉祥：为主播点赞了`、`只剩下些许沉默：这队伍废了…`、`与光同行：为主播点赞了`、`谁还不是少年：为主播点赞了`。

## 实际边界（重要）

| 现象 | 说明 |
| --- | --- |
| 人数不涨 | 直播间在线人数**按账号去重**，同一账号从多个入口进同一个房间只算 1 人；多开只是"你个人多看了几个房间"。 |
| 有效观看时长 | 靠播放器真实播放才算，纯挂心跳不算。 |
| 资源占用 | 每路都要真实解码，CPU/内存/带宽按房间数线性上涨；一般 4–9 间比较舒服。 |
| 风控 | 同账号短时间大量进房、非常规 IP、只有心跳没有播放行为，都可能触发验证码/静默踢出/功能限制。**撑多久只能自己实测。** |
| 合规 | 抖音用户协议禁止自动化批量访问与挂机；自用监控可以，做成对外产品（尤其刷人气、挂机涨亲密度）属于违规范围。 |

验证"是否真的同时在房间里"的最快办法：随便挑两个房间，看自己头像是否出现在两个房间的观众/榜单里，并放置 10 分钟以上看会不会被静默踢出（表现为画面还在但弹幕不再更新、或进房提示消失）。

## 关于弹窗（曾经的坑）

早期版本对页面里的 `window.open` 一律新开窗口，而抖音直播间里塞了大量引流跳转（广告落地页、`/search/` 搜索页），结果会不停弹出一堆"抖音搜索"窗口。

现在 `shouldOpenAux` 的规则：

| 情况 | 处理 |
| --- | --- |
| 非 `douyin.com` 域名 / 广告落地页 | 拦掉，不开窗 |
| `douyin.com/search/*`、`/discover/*` | 拦掉（直播间里的搜索跳转基本都是引流） |
| 同一路径 30 秒内重复 | 去重，不重复开 |
| 辅助窗口总数 ≥ 3 | 不再开新窗 |
| 正常抖音页面（如另一个直播间） | 允许，共享同一登录态 |

## 结构

## 想换实现路径

| 声音卫兵日志 | `%APPDATA%\ParallelRoom\guest-guard.log` | 常开，512 KB 轮转；只有"真的关掉了一个遗留页面"时才写，见「关掉房间后还有声音？」 |

> ⚠️ **正在写的那个 part，在资源管理器里会一直显示 0 字节**——这是 Windows 的行为：文件被 ffmpeg 占着的时候目录项大小不更新，只有这一段关闭（滚到下一段 / 停止 / 进程退出）时才会一次性刷出真实大小。实测：`part001.mkv` 显示 0 字节，实际写了 740 MB，滚段瞬间变成 740.2 MB。
>
> 也正因为这点，**卡死检测不能看文件大小**（会一直判"没长"→ 把好录制杀掉）。已改为看 ffmpeg 自己打的 `time=HH:MM:SS` 进度：实测 90 秒里进度 4→14→27→36→58→91→97 秒连续前进（`idleSec` 0–1），不误杀；用一个"进度停在 2 分钟前"的假录制验证，看门狗正确杀掉并重连（`killed=1`），而进度新鲜的（5 秒前）`killed=0`。

实测：2026-10-30 16:55 同时录了 3 个房间，17:07 重启时被自动收尾并合段，输出各自一个 mp4：

```
Dota孤城大神_165542.mp4   79 MB   644s  hevc 1920x1080  (3 段合并)
DOTA情怀_165549.mp4      1706 MB  638s  h264 1920x1080  (3 段合并)

```

### 录制选项（一个菜单管全部录制参数）

工具栏上只有一个 **`⚙ 录制选项`** 按钮，按钮上直接写着当前配置（`⚙ 录制选项 · 5 分钟/段 · 自动合并`），点开就是这张表里的全部参数 —— 原来散在工具栏的「录制目录」「录制参数」「留分段」三处入口合并到这里，不再各改各的：

| 参数 | 默认 | 说明 | state.json |
| --- | --- | --- | --- |
| 录制目录 | 项目下 `output/` | 每场录制在里面建 `<主播名>_<时间戳>/` 子目录，分段和成片都在里面 | `recOutDir` |
| 分段时长 | 5 分钟 | 1 / 2 / 3 / 5 / 10 / 30 分钟或不分段；只影响"落盘粒度"，不影响成片 | `recSegmentMs` |
| 录完怎么处理 | 自动合并 | **自动合并成一个 mp4**（`-c copy` 纯转封装，几秒）/ **保留分段**（part0000.mkv… 留着，自己在「剪辑」页合并） | `recKeepParts` |
| 最长录制时长 | 60 分钟 | 单场录制到点自动停止并保存成片；**0 = 不限** | `recMaxDurationMs` |
| 磁盘余量保护 | 2048 MB | 剩余空间低于这个值就拒绝开录（正在录的在降到 0 前会先被看门狗停掉） | `recMinFreeMb` |

分段时长和"录完怎么处理"是两件事：分段是**防丢失**（断电/强杀最多丢最后一段），合并是**停止时**那一步。所以"1 分钟分段 + 自动合并"是默认组合，跟"每 1 分钟产生一个独立成片"不是一回事（后者用瓦片上的「✂ 分段」）。

实测（沙箱实例，沙箱目录里跑，14 秒一场、分段 6 秒）：

```
自动合并：目录里只剩 自动合并烟雾测试_20261030-234959.mp4      4,006,913 字节
保留分段：目录里是 part0000.mkv 1,763,905 / part0001.mkv 2,281,607 / part0002.mkv 1,447,955
          + .keep-parts.json（标记这个目录故意不合并，下次启动的收尾逻辑会跳过它）
磁盘保护：把安全线设成 1TB → startRecording 直接返回
          「磁盘剩余 16.0 GB，低于安全线 1024.0 GB，请清理空间或换录制目录」
时长上限：设成 0 → getOptions 回 0，armDurationTimer 不再挂计时器（真的不限）
```

菜单里改任何一项都会立刻落到 `state.json` 并同步给录制模块；改"最长录制时长"时，**正在录的那几路也会按新上限重新计时**（不用等下次录制）。

### 分段时长可定制

「⚙ 录制选项」按钮上直接写着当前档位（例如 `⚙ 录制选项 · 5 分钟/段 · 自动合并`），点开就是下拉框：

| 档位 | ffmpeg |
| --- | --- |
| 1 / 2 / 3 / 5 / 10 / 30 分钟 | `-f segment -segment_time 60/120/180/300/600/1800 …` |
| 不分段 | 不用 segment 复用器，整场一个文件 |

选择存在 `state.json` 的 `recSegmentMs`，重启保留。分段按**关键帧**切，实际长度可能比设定值略长一点（比如设 1 分钟，实测切出来 60–63 秒）。

实测（沙箱实例，录制 9 秒）：

```
segmentChoices = [60000,120000,180000,300000,600000,1800000,0]   当前 = 300000
1 分钟   → ffmpeg 命令行含 -segment_time 60  且 -f segment  ✅
不分段   → 无 -segment_time、不用 segment 复用器              ✅
两个测试目录都落在 D:\code\ParallelRoom\output\分段1分钟_…\ 与 …\分段不分段_…\，里面各有一个 mp4
```

> 文件名编号改成 4 位（`part0000.mkv`）：1 分钟一段、录十几个小时也不会出现 `part1000` 排到 `part999` 前面的乱序。

**默认分段目录**就是 `D:\code\ParallelRoom\output`（实测 `getOptions().outDir = D:\code\ParallelRoom\output`）。默认值的兜底顺序：`app.getAppPath()/output` → `exe 同目录/output` → 源码目录 `/output`，所以换个位置跑也不至于把分段塞到系统临时目录。每场录制的分段在它的子目录里：`output\<主播名>_<时间戳>\part0000.mkv …`。

### 合并 + 水印一步做完（实测）

「合并时一起加水印」用的是 **concat 滤镜**而不是 concat 解复用器：各段的 `v/a` 先接成一路（`concat=n=2:v=1:a=1`），再接到水印滤镜图上，最后只编一次。

```
[0:v][0:a][1:v][1:a]concat=n=2:v=1:a=1[cv][ca];
[cv]drawtext=fontfile='…msyh.ttc':text='合并水印':fontcolor=0xFFCC00@0.85:…[t];
[t]null[vout]
```

代价：音频也得跟着重编码（concat 滤镜输出未压缩帧），所以是 `-c:a aac`；纯合并那条路仍然是 `-c copy`，几秒钟完事。

实测（同一段 20.3 秒的录制复制成两段当输入）：

| 操作 | 耗时 | 输出 | 时长 | 右下角区域采样 |
| --- | --- | --- | --- | --- |
| 纯合并（copy） | 0.4 秒 | 121 MB | 40.5s | `RGB(55,84,95)` 与原片一致 ✅ |
| 合并 + 文字水印 | 6 秒 | 61 MB | 40.5s | `RGB(60,85,90)` 偏黄 ✅ |
| 合并 + 图文水印 | 7 秒 | 58 MB | 40.5s | 左下角 `RGB(65,86,66) → RGB(227,231,0)` ✅ 黄色 logo 明显叠上 |

时长 40.5s = 2 × 20.3s，说明两段真的接上了。

**限时水印**（`fromSec`–`toSec`）用纯色源做了对照实验，排除画面内容干扰：

```
纯色源（灰底 48,48,48）+ 居中黄字 + enable='gte(t\,5)*lte(t\,10)'
  t=2   窗口外: RGB(50,47,50)   ← 灰底
  t=7   窗口内: RGB(59,55,45)   ← 黄字在
  t=13  窗口后: RGB(50,47,50)   ← 回到灰底
```

### 大分段（录制中拆分，不停止录制）

瓦片标题栏现在是 **两个明确动作 + 录制中多一个「分段」**：

| 状态 | 按钮 |
| --- | --- |
| 没在录 | `● 开始` |
| 录制中 | `■ 结束`　`✂ 分段` |

点「✂ 分段」= **把已经录的收成一段存好，同时立刻接着录下一段**：

```
录制目录\主播名_180136\      ← 第 1 段（点分段后立刻合并成 mp4）
录制目录\主播名_180146\      ← 第 2 段（紧接着开始）
录制目录\主播名_180158\      ← 第 3 段（再点一次分段）
```

顺序上故意先起新的、再合并旧的，这样合并那几秒不占用录制时间：

1. 记下当前流地址
2. 让旧 ffmpeg 正常退出（`q`）
3. **立刻**用新目录 + 新时间戳起新 ffmpeg
4. 后台把旧目录的分段合并成 mp4

实测（直录流，连续 3 次分段）：

```
第 1 次  旧ffmpeg关闭 +89ms   split() 返回 +108ms   新段第一帧 +1453ms
第 2 次  旧ffmpeg关闭 +220ms  split() 返回 +239ms   新段第一帧 +1096ms
第 3 次  旧ffmpeg关闭 +215ms  split() 返回 +233ms   新段第一帧 +1077ms
```

也就是点下去到新的一段真正开始收到画面，**间隙约 1.1–1.5 秒**（这 1 秒多是重新拉流、等首帧的时间，无法再压缩）。追求"一帧不丢"就得走另一条路（全程单体录制、停止后按时间戳切），这个没做。

完整的「开始 → 分段 → 再分段 → 结束」实测：

```
10:01:36 开始    目录 分段链路_180136
10:01:46 分段#1  旧目录 12 秒后变成 分段链路_180136.mp4 (37MB)；新目录 分段链路_180146 开始
10:01:58 分段#2  180146 → mp4 (49MB)；新目录 分段链路_180158
10:02:10 结束    180158 → mp4 (42MB)
最终三个目录各一个 mp4，actives = 0
```

**屏幕/整窗录制也支持分段**（重构了媒体流的路由：`MediaRecorder` 的消息现在带 sessionId，新旧两路各写各的 webm，靠 sid 分流，不会串台）。实测：

```
10:09:34 屏幕录制开始  sid=smvut8y2o6zuj  canvas 1188x684
10:09:43 分段        旧 sid 后台转码 → 屏幕测试_180934/…mp4 (3032KB, 117 帧)
                    新 sid=smvut956sqn1a 立刻起来（+109ms，+200ms 就 ready）
10:09:52 结束        新段 → 屏幕测试_180943/…mp4 (2862KB, 234 帧)
```

屏幕录制的切换比直录流更快（同一个 display 源，不用重新拉流）。顺带统一了目录：屏幕录制的成片现在也放进 `<主播>_<时间戳>/` 子目录，和直录流一致。

几个行为细节：

- 分段后状态栏显示 `● 录制中 N 路(流) 第K段 00:12`，能看出这是第几段
- 分段很密也不会串：每次 `finalizeSession` 只摘自己那一路，不会把刚起的新段从"录制中"里删掉（这是这次修的坑）
- 刚起录不到 10KB 就点分段：这一小段会被丢弃（数据太少封装不出东西），新的一段照常开始
- 「结束」仍然是彻底停止并保存最后一段

### 「保留分段」模式（不合并成 mp4）

「⚙ 录制选项」→ **录完怎么处理 → 保留分段（自己合并）** 选上，停止时就不合并、不删除，直接把分段留着：

```
output\保留分段_20261030-182003\
    .keep-parts.json     ← 标记（有它，启动恢复不会自作主张合并）
    part0000.mkv   8.37s  25MB
    part0001.mkv   4.20s  13MB
    part0002.mkv   4.18s  13MB
    part0003.mkv   1.04s   3MB
```

实测（分段 5 秒、录 13 秒、勾上保留）：

```
[keep] 停止后目录内容 = [".keep-parts.json","part0000.mkv","part0001.mkv","part0002.mkv","part0003.mkv"]
[keep] 标记内容 = { "label":"保留分段", "parts":4, "bytes":55799684, … }
[keep] recoverOrphans -> {"ok":true,"recovered":0}   ← 重启恢复跳过它，没被合并掉
[keep] listRecordings = part0003/0002/0001/0000（pending:false，可多选）
```

想用的时候去「剪辑」页签把这几个 part 选起来合并即可（`-c copy` 纯封装）。实测 4 个分段 → 17.8 秒 / 53 MB，时长等于各段之和。

> 补充：为什么"1 分钟分段"默认看不到单独文件——小分段是**防丢失**用的内部机制，默认在停止时合并成一个 mp4 再删掉分段。要看到并保留分段，就是上面这个开关。想要"每 N 分钟一个独立成片（各自一个目录）"，那是大分段自动化，目前只有手动「✂ 分段」按钮。

> 「保留分段」现在只有一个入口：**「⚙ 录制选项」→ 录完怎么处理**（原来是工具栏 `☐ 留分段` + 弹窗两处，容易各改各的）。开着的时候，工具栏按钮会显示成 `⚙ 录制选项 · 5 分钟/段 · 保留分段`，录制中的状态栏也会带上 `· 保留分段`。
>
> 顺带修了个真 bug：窗口一窄，工具栏这套控件会**横向溢出**，最右边那些按钮被挤出可视区，压根点不到——实测 986 宽时「留分段」在 x=1051，已经在窗口外面了。原因是 `.tools` 是个 `flex: 0 0 auto` 的项，按内容宽度撑开、自己不换行。改成 `flex: 1 1 auto; min-width: 0; flex-wrap: wrap` 后，实测 1700 / 1200 / 1000 三档宽度下 `offscreen: []`，一个控件都不出界。（合并成一个「⚙ 录制选项」按钮之后工具栏更短了，更不容易挤。）

### 剪辑页签的三处改进

**1）合并后的文件名默认 = 目录名（`<主播名>_<时间戳>`）**

以前默认是 `<第一个文件名>_合并_<时间戳>`（就是你那次合出来的 `part0003_合并_水印_20261030-183536.mp4`），现在默认直接用文件所在目录的名字，和普通录制的成片命名一致：

```
output\主播A_20261030-180000\part0000.mkv …  ← 选中这些合并
output\主播A_20261030-180000\主播A_20261030-180000.mp4   ← 默认输出名
```

- 输出框留空时，placeholder 会直接显示 `留空 = 主播A_20261030-180000`
- 文件在录制目录根上（没有自己的子目录）时，退回 `<文件名>_合并`
- **不覆盖已有同名成片**：撞名就自动变 `..._合并.mp4`、`..._合并2.mp4`
- 合并结果仍写在**同一目录**里，所以合并前后天然在一起

**2）合并后的和合并前的显示在一起**

原来列表是"全局按修改时间倒序"，同一个目录的成片和分段会被别的目录的文件插到中间，看起来东一个西一个。现在改成**先按目录分组、组内再按时间倒序**，并用标签区分：

```
dota老花一打九_20261030-183044                    [全选本组]
    dota老花一打九_…183044.mp4        [成片]  131.9 MB
    part0003.mkv                     [分段]   28.3 MB
    part0002.mkv                     [分段]   38.5 MB
    part0001.mkv                     [分段]   38.0 MB
    part0000.mkv                     [分段]   14.2 MB
dota老花一打九_20261030-183431                    [全选本组]
    dota老花一打九_…183431.mp4        [成片]  236.6 MB
```

实测：分组头 4 个、每组的「全选本组」按钮都在；标签正确；合并后新成片 `isOutput=true` 排在该组最前、紧跟未合并的分段。

**3）选中目录下所有文件**

- 面板右上角的 **`☐ 全选全部`** —— 一次选中当前目录下**所有子目录**里的全部视频文件（实测 `已选 8`，8 个文件全勾上）
- 每个分组头右侧的 **`全选本组`** —— 只选这一个目录的文件；已经全选时再点一次就整组取消（实测 8 → 点本组按钮 → 7）
- 录制中的目录（`（录制中）N 个分段`）依然不可选，避免把正在写的文件拿去合并

顺带修的一处：`.tools` 工具栏容器窗口一窄会横向溢出，最右边的按钮（停止录制 / 全屏 / 清空…）被挤出可视区。改成可换行后，实测 1700 / 1200 / 1000 三档宽度下 `offscreen: []`。（后来工具栏上那一堆录制控件又合成了一个「⚙ 录制选项」按钮，更宽松了。）

### 水印的速度、漂移、字体、只给前 N 个

#### 速度（实测，本机 RTX 5060 Laptop + Ryzen 9 8945HX）

基准：60 秒 / 1920×1080 / 30fps，加一行文字水印，重编码：

| 编码器 | 墙钟 | 相对实时 | 输出体积 |
| --- | --- | --- | --- |
| **libx264 veryfast crf21**（默认） | **4.1 秒** | **14.8×** | 44.4 MB |
| libx264 ultrafast crf21 | 2.3 秒 | 26.6× | 114.1 MB（体积翻倍，不划算） |
| **h264_nvenc p1 8M**（显卡） | **2.0 秒** | **31.8×** | 57.5 MB |
| h264_nvenc p4 cq23 | 3.1 秒 | — | 72 MB |

换算成日常感受：**10 分钟的录像，默认设置约 40 秒加完水印**（显卡约 20 秒）；30 分钟约 2 分钟（显卡约 1 分钟）。瓶颈是 x264 编码，不是 drawtext。

所以剪辑页里给了「编码器」下拉：
- **软件 x264（体积小）** —— 默认，crf 21
- **显卡 NVENC（快一倍）**—— `-preset p1 -b:v 8M`，本机实测可用（`h264_nvenc` 已确认存在）

#### 漂移水印（新）

「漂移」下拉：不动 / 横向滚动 / 纵向滚动 / 斜向滚动 / 满屏反弹，配「漂移速度」（像素/秒）。实现是 drawtext 的 x/y 时间表达式：

```
横向滚动  x='w-mod(t*200\,w+tw)'          y='(h-th)/2'
斜向滚动  x='w-mod(t*200\,w+tw)'          y='h-mod(t*120\,h+th)'
满屏反弹  x='(w-tw)*abs(sin(t*0.400))'    y='(h-th)*abs(cos(t*0.300))'
```

图片水印（logo）同样支持漂移（overlay 的 W/H 变量版本）。选了漂移就不用管「位置」了。

实测（纯色背景 + 绿字斜向漂移，所以像素变化只可能来自水印）：

```
固定水印   右下角 t=0.5/2/4 : RGB(53,62,54) 恒定，左上角恒为源色 RGB(35,51,64)
斜向漂移   左上角 t=0.5/1.5/2.5 : RGB(35,51,64)  → t=3.5 : RGB(35,59,64)（绿字漂过这里）
```

#### 字体可换（新）

剪辑页多了「字体」下拉，列出系统里**实际存在**的 14 个字体：微软雅黑 / 雅黑粗体 / 雅黑细体 / 黑体 / 宋体 / 楷体 / 仿宋 / 等线 / 等线粗体 / Consolas / Arial / Arial Black / Impact / Times New Roman，另有「自定义」按钮可以选任意 `.ttf/.ttc/.otf`。

同一段文字在四种字体下的渲染指纹（裁文字区域取 MD5）互不相同，说明字体真的生效：

### ⚠️ 三个"以为录失败"的坑（已改）

用户反馈：点某个房间的「● 开始」后画面直接放大（以为全屏了），`output` 里也没有对应目录；接着点「录窗口」也没看到文件。查下来是这样：

| 现象 | 真实原因 |
| --- | --- |
| 点录制后画面放大 | 那个房间刚打开，**还没抓到直播流地址** → 退化成屏幕录制 → 屏录制要把这块放大才有清晰度（不是全屏，是把该瓦片铺满） |
| `output` 里没有目录 | **屏幕录制要"停止之后"才开始转码出 mp4**；录制中只有 `%TEMP%\ParallelRoomRec\xxx.webm` 在长（实测 3.5 分钟长到 375 MB），停止后转出 466.6 MB 的 mp4 |
| 点「录窗口」没反应 | 屏幕/整窗录制**同时只允许 1 路**，槽位被上一个屏录制占着 → 请求被拒（原来只弹一句"同时只能 1 路"，看不出是谁占的） |

1. **点录制先等流地址**：如果这个房间还没有流地址，先等最多 8 秒（每秒重查一次），一抓到就用**直录流**（原画、不放大画面）；8 秒还没有才退化成屏幕录制
2. **占用提示带上名字**：录窗口被拒时返回
   `「为何你我他」正在屏幕录制中，屏幕/整窗录制同一时间只能 1 路 —— 先点它的「■ 结束」再录这个`
   同时用 `notice()` 推到状态栏，并写进 `rec.log`（`screen record rejected`）
3. **状态栏说明屏幕录制要等停止**：`● 录制中 1 路(屏) 第1段 00:12 · 屏幕录制（停止后才生成 mp4）`
4. **rec.log 补全**：`screen record start` 也写进日志（原来只有 done），以后屏幕录制的问题能直接回溯

另外给 `toggleRecord` 加了防连点：等流地址那 8 秒里再点「开始」只提示「正在启动录制」，不会起两路。

### 单房间不再退化成屏幕录制 + 整窗录制的红框提示

**改动一：单房间只走直录流，抓不到就报错让你重试**

之前抓不到流地址会偷偷退化成屏幕录制——那条路要放大这块画面、清晰度还受窗口限制，用户看到的就是"点了录制就全屏了"，而且屏幕录制要停止后才出 mp4（录制中 `output` 里什么都没有）。

| --- | --- |

| 8 秒还没有 | **报错，不录**：`还没抓到这个房间的直播流地址：先点这个瓦片的「⟳」重载房间，等画面出来再点「● 开始」（不会退化成屏幕录制）` |
| 主进程侧兜底 | 非 `forceScreen` 且没有流地址 → 直接 `{ok:false}`，**根本不会进屏幕录制那条路** |

屏幕捕获现在**只服务于「录窗口」**这一个功能。实测：

- 顶部中间一个红底胶囊：`● 正在录制整个窗口 00:03（点「停止录窗口」结束）`，时间实时走

**红框会不会被录进画面？** 不会 —— 整窗录制裁的是各瓦片 `.stage` 的矩形（不含工具栏/标题栏/瓦片间隙），而这些矩形离窗口边缘有 6px，4px 边框在外侧。实测 `minMarginToEdge: 6, borderWouldBeCaptured: false`。另外加了个保护：**一个瓦片都没开时直接拒绝整窗录制**（那种情况会退化成录整个窗口，边框就会被录进去，而且也没什么可录的）。

### 整窗录制的三个 FAQ（都实测过）

**Q1：整窗录制的声音从哪来？需要安静吗？**

`getDisplayMedia` 的录音走的是 **系统回环（audio: 'loopback'）**，也就是**电脑正在播放的全部声音的混音**：所有房间的直播声、QQ/微信提示音、你放的音乐，全都会进去。**不采麦克风**，所以"屋子里安不安静"没有影响。

| 想要的效果 | 该用哪个 |
| --- | --- |
| 只保留某一个房间自己的声音 | 用瓦片上的「● 开始」**直录流**——那条路 `-c copy` 拿到的是该房间独立的音轨 |
| 一次录多个房间拼成一张画面（声音是混音） | 「录窗口」/ `Ctrl+Shift+W` |
| 录窗口但不想录到别的声音 | 录制期间别在电脑上放别的音源（系统提示音也会进） |

**Q2：「正在录制整个窗口」的提示被录进画面了 —— 已修**

原因：整窗录制不是录整个窗口，而是把各瓦片 `.stage` 的矩形**裁出来拼成一张干净画面**。全屏 + 工具栏收起时，瓦片会贴到窗口边缘，顶部中央那行胶囊正好压在瓦片视频区上，于是被裁进去了。

现在的做法：每次开始录窗口都先算一遍胶囊会不会压在瓦片上 ——

- 顶部安全 → 放顶部
- 顶部不安全 → 挪到底部
- 都不安全 → **整个隐藏**，只留贴边红框

实测（真实布局 / 假造"瓦片贴满窗口"的最坏情况）：

```
真实布局       → top（放顶部）
瓦片贴满窗口   → hidden（display:none，只留边框）
```

边框本身录不进去：它是 4px 贴在窗口最外沿，而瓦片区域离窗口边缘还有约 6px（`#grid { padding: 6px }`）。实测 `borderPx: 4, minMarginToEdge: 5.99, borderInsideCrop: false`。

**Q3：鼠标划过会被录进去吗？—— 会**

实测 `MediaStreamTrack.getSettings().cursor = "motion"`，也就是**鼠标移动时会被画进画面**。我加了 `getDisplayMedia({ video: { cursor: 'never' } })` 并额外 `applyConstraints({ cursor: 'never' })`，但这套 Chromium 对窗口源忽略了这个约束（设置值仍是 `motion`）。`rec.log` 里现在会记一行 `screen capture settings {cursor: "motion"}` 方便确认。

规避办法（按效果排序）：

1. **用「● 开始」直录流** —— 直接抓流，根本不存在光标问题，这也是画质最好的路
2. 录窗口期间别把鼠标划过瓦片画面区（裁剪只取瓦片区域，把鼠标停在工具栏或画面外就录不到）
3. 让鼠标停在屏幕边缘 / 用触控板少动

真正的"录窗口且不要光标"需要 OS 层能力（Windows 下隐藏系统光标），Electron 没有暴露，我没有做。

### ⚠️ 「某个房间点录制总是不成功」的真凶：被 HLS 分片地址顶掉了 FLV

现象：2×2 布局里点某个房间的「● 开始」，看起来没反应；`output` 里只有几个 2.6 MB 的小分段。

查 `rec.log` 发现那个房间是这样循环的：

```
stream record start {url: "https://pull-hls-l11-admin.douyincdn.com/byte-dance-cq/<hash>/6764832"}
stream ffmpeg exited unexpectedly {code: 0, tail: "frame=120 ... time=00:00:03.93 speed=6.88x"}
stream will resume {attempt: 1..5}
stream retries exhausted → 放弃
```

原因链条：

1. 抖音给这个房间下发的流是 **HLS 分片**（`pull-hls-...` 且没有 `.m3u8` 后缀），不是 HTTP-FLV
2. 老的抓流逻辑**只保留"最后一条命中的 URL"**，播放器后发的这条 HLS 分片把先前正确的 FLV 地址**顶掉了**
3. ffmpeg 拿这个分片当输入 → 下载 3.9 秒 → **正常 EOF（退出码 0）** → 被当成"断流" → 自动续录又拿同一个地址再录 4 秒 → 5 次后放弃

修复两处：

| 改动 | 说明 |
| --- | --- |
| 候选地址按类型优先级挑 | sniffer 现在给每个页面留最多 8 条候选，取用时按 **FLV > m3u8 播放列表 > hls 无扩展名分片** 排序；老的"最后一条"不再是决定因素 |
| 短流立即放弃 | 如果这一次只录到 **< 15 秒就正常结束（退出码 0）**，说明这个地址本来就不是可连续拉的直播流 → 立刻停止并报错：`这个流地址只持续了 N 秒就结束了（地址类型：hls-分片），不是可连续拉的直播流。点这个房间的「⟳」重载后重新录制试试`，不再白等 5 次重试（约 3 分钟） |

实测：

```
只有 FLV                              → kind=flv
FLV 早、HLS分片晚（真实踩坑场景）      → kind=flv   ✅ 选的是 FLV
只有 HLS 分片                          → kind=hls-other（确实没有别的可选）
m3u8 播放列表 + FLV                    → kind=flv   ✅

短流分支（code=0、attemptMs=4002、hls-分片）
  → stream address not seekable/live, give up
  → actives=0  pendingResumes=0   ✅ 没有进入重试
```

> 另外确认：4 个房间**首次加载**的时候抓到的是清一色 FLV 地址（`pull-flv-*` / `*.douyincdn.com/thirdgame/stream-*.flv`），说明 FLV 本来是有的，纯粹是被后来的 HLS 分片覆盖了。

### 弹幕默认关 + 回声的真凶（同一房间开了两次）

**1）界面里还看得到"用户发言"—— 那是我们自己的弹幕面板，已默认关**

实测（用你真实 profile 读的）：`showDanmu` 之前是 `true`，4 个瓦片的 `.danmu-panel` 全是可见的，里面就是「吉娃娃（大佬皓）：找个喜欢当内鬼的…」这类聊天。

现在默认值改成**关**：

```
showDanmu: false   按钮: 「弹幕面板：关」   4 个面板全部 hidden
```

想看得时候点一下「弹幕面板」就行（选择会记住）。同时实测抖音页面**自己**的弹幕层在纯净模式下是干净的：

```
[class*="danmu"|"comment"|"chat"|"message"|"msg"|"barrage"] 候选 9 个 → 可见 0 个
```

**2）2×2 声音都开时的"回声"—— 真 bug：同一个直播间能开两个瓦片**

实测每个瓦片里只有 **1 个 `<video>`、0 个 `<audio>`**，不存在"一路声音播两遍"的代码问题。真正的原因是**去重逻辑漏了 URL 的 query**：

```js
// 原来
const bareUrl = (u) => String(u || '').replace(/\/+$/, '').toLowerCase()
```

于是 `live.douyin.com/123` 和分享来的 `live.douyin.com/123?enter_from=share&is_share=1` 被当成**两个不同房间** → 同一个直播间开了两个瓦片 → 同一路声音播两遍、两边延迟不同 → 听起来就是回声。

现在按**房间号**去重（认不出房间号才退回"去 query/hash 的 URL"），并且在 `addRoom` 里加了一道硬拦：

```
加 https://live.douyin.com/489648167418?enter_from=share&is_share=1
→ tilesBefore: 4, tilesAfter: 4
→ 状态栏：这个直播间已经在看了（同一个房间只开一个瓦片，避免声音重叠）
```

> 另外提醒：**4 个不同直播间同时出声本来就是混音**（4 个解说叠在一起），那种"糊"不是回声。想让声音清楚，只留一路有声、其它点 🔇 或直接「全静音」。

### 每个直播间独立音量

原来每个瓦片只有「🔇 静音/出声」这一档（外加「全静音/全出声」）。现在瓦片标题栏里多了一个**窄音量滑块（0–100%）**，每个房间单独控制。

实现要点：抖音页面自己会把 `video.volume` 设成 0.6，所以不能只设一次——`guestScript` 每一轮（4 秒一次的心跳）都会把音量纠正回你要的值，和静音逻辑同一套机制。

实测（3 个瓦片分别设 100% / 30% / 静音）：

```

6 秒后页面实际值   [{vol:1,muted:false}, {vol:0.3,muted:false}, {vol:1,muted:true}]
界面同步          sliders=["100","30","100"]   icons=["🔊","🔉","🔇"]
记住的房间音量     {"room:489648167418":1, "room:24168746439":0.3}
```

- 音量按**房间号**存在 `localStorage.pr.prefs.volumes`，同一个房间下次打开还是这个音量
- 音量拉到 0 会自动标成静音（图标 🔇）；从 0 往上拉会自动取消静音
- 滑块在**瓦片标题栏**里，而录制（单房间直录流 / 整窗录制）裁的都是 `.stage` 视频区，所以**滑块不会被录进画面**
- 声音再多路也是混在一起从同一个输出设备出来的，所以"4 路都开"依旧会互相盖住——独立音量只是让你能按比例调，不是把 4 个声音分开听

### ⚠️ 合并顺序原来会错（已修）

**结论：确实有问题。** 合并用的是**你勾选的顺序**，而列表是按时间**倒序**渲染的——所以用「全选本组 / 全选全部」选出来的文件，拼出来是**倒放**的。

用三段纯色片段（part0000=红、part0001=绿、part0002=蓝）做的对照实验：

| 拼法 | t=1s | t=4s | t=8s | 结论 |
| --- | --- | --- | --- | --- |
| 按勾选顺序拼（**旧行为**，勾选顺序 part0002→0001→0000） | 蓝 `RGB(0,0,255)` | 绿 `RGB(0,255,1)` | 红 `RGB(254,0,0)` | ❌ 整段倒放 |
| 按修改时间升序拼（**现在**） | 红 `RGB(254,0,0)` | 绿 `RGB(0,255,1)` | 蓝 `RGB(0,0,255)` | ✅ 正常 |

修法：

1. `mergeRecordings` 里加 `sortByTime()`：**修改时间升序 + 文件名**兜底，这才是录制发生的真实时间顺序；勾选顺序、列表顺序都不再影响拼接
2. `rec.log` 的 `manual merge start` 里现在带 `order` 字段，出问题能直接看拼的顺序：
   ```
   manual merge start {files:3, order:["part0000.mkv","part0001.mkv","part0002.mkv"]}
   ```
3. **剪辑列表里给选中的行标号 `#1 #2 #3`**，就是最终的拼接顺序，点「合并」之前就能核对（列表本身的排列顺序不代表拼接顺序）

实测（故意倒序勾选）：

```
传入顺序（勾选顺序）: ["part0002.mkv","part0001.mkv","part0000.mkv"]
rec.log order       : ["part0000.mkv","part0001.mkv","part0002.mkv"]
合并后时长           : 9.000 秒（三段 3 秒）
内容                 : t=1 红 → t=4 绿 → t=8 蓝   ✅
```

> 顺带说明：**中途停止/断电后自动合并的那条路**（`finalizeSession` → `mergeParts`）一直是按 `part0000, part0001, …` 文件名排序的，没有这个问题。只有"手动选文件合并"这条路错了。
